Overview & goal

htmldocs produces self-contained .html files committed under docs/ across an organization's repos. The goal here is team reviewability: any teammate should be able to open a doc from any branch or PR in a browser, read it rendered, and leave inline review comments — but only for repos they can already see on GitHub. No clone, no checkout, no build step.

The design is a single Cloudflare Worker that fronts the whole org. On request it (1) logs the viewer in via GitHub, (2) fetches the requested doc from GitHub using that viewer's own credentials, (3) injects the review-mode UI into the HTML, and (4) serves it. Authorization is not a separate system — because the fetch uses the viewer's credentials, GitHub itself is the authorization engine: a repo the viewer can't access simply returns 404, which also avoids leaking that the repo exists.

Design stance: source-agnostic. GitHub is the first implementation, not a hardcoded assumption. The Worker is built around three seams — OAuthProvider, DocSource, ReviewStore (see Abstractions) — so a future GitLab/Bitbucket/raw-S3 source slots in without rewriting the Worker.

Two deliverables. D1 is the proxy with auth working as we expect — log in, fetch any branch as the user, render. D2 adds the review pieces (inject UI + comment store). D1 is the de-risking milestone; D2 builds on a proven D1.

The review half is the hosted, org-wide equivalent of the skill's existing local review server (serve.sh / review mode), which already injects a comment UI into a doc served on localhost. See also the design notes in review_system.html.

Core decision: a Worker, not Pages

The original framing was "put Cloudflare Pages in front of the repos." We are not using Pages. Cloudflare Pages serves pre-built static files frozen from a branch at build time — it cannot make a per-request decision like "fetch this as this user, then decide whether to show it." That dynamic, per-request behavior is exactly what a Worker is for. A Pages Function is itself just a Worker bolted onto a Pages project, so "Worker" is the honest name for what we build.

Pages-based approachWhy it doesn't fit
One Pages project per repo, branch previews~100 projects/account soft limit; an org has more repos. Build minutes consumed per branch. No per-user authorization — Access only gates who logs in, not which repo they may see.
Cloudflare Access in front of *.pages.devAccess (GitHub IdP) conveys identity + org/team membership only — never per-repo permission. A user in the org could view a repo they have no access to.
"Any branch" renderingPages previews are tied to deployments, not arbitrary refs. A Worker reads ?ref={branch} directly — "any branch" comes for free.
The key insight. Fetching the doc with the viewer's GitHub token collapses authentication and authorization into one step. We never ask "can Alice see repo X?" — we just try to fetch it as Alice and let GitHub answer. This removes an entire class of problems: no permission cache to keep fresh, no stale access after a permission is revoked, no risk of the gate disagreeing with GitHub.

Architecture at a glance

Three GitHub-side pieces of plumbing make this work, all owned by one GitHub App (an identity, not a server): the OAuth flow that logs the viewer in, the user-to-server token used for the fetch, and an optional installation token used only to post a review summary back to a PR. Those three map onto the three abstractions below.

Abstractions & responsibilities

The Worker depends on three interfaces, never on GitHub directly. GitHub is one adapter that implements all three. This keeps the request pipeline (auth → fetch → inject → store) generic and makes a second source a matter of writing one adapter, not touching the Worker.

Why OAuthProvider, not a generic AuthProvider. The interface bakes in the OAuth authorization-code flow on purpose. The whole design rests on the Worker holding the user's delegated token to fetch as them — a non-token scheme (SAML, header-proxy) would authenticate the user but hand us nothing to call the source with, breaking the model. So OAuth is load-bearing, not incidental; and every realistic second source (GitLab, Bitbucket, Google) is OAuth too, so the specific name costs nothing.

AbstractionResponsibilityGitHub implementation (V1)
OAuthProvider Run the OAuth login; mint & verify the CSRF state; produce & refresh a credential; say who the user is. Declares its own redirect target(s); the Worker mounts them. GitHub App OAuth (user-to-server token, 8h + refresh). beginLogin → {authorize URL, state}; completeLogin → token.
DocSource Fetch a doc at (repo, ref, path) using the viewer's credential. NotFound is the authz answer. Optionally resolve a ref to a commit SHA. Contents API ?ref={branch} as the user; 404 = no-access-or-missing (non-leaking).
ReviewStore List/create/resolve comments keyed by a doc identity. out of scope for D1 — the interface below is provisional and likely to change as Deliverable 2 is designed; shown only so D1 doesn't foreclose it. D1 + a Durable Object per doc. Optional later reflector that posts as the user to GitHub reviews.

How OAuthProvider and DocSource relate

The two interfaces are coupled by the Credential, not by identity: the provider produces a credential and the source consumes one. They line up only when the credential the login mints is the same token the source needs to fetch — which is exactly the GitHub case (a GitHub user token is what the Contents API wants). That alignment is the whole source of the free-authz property: "fetch as the user" works precisely because the auth token and the fetch token are one and the same, so GitHub's 404 becomes the authorization answer.

PatternCredentialAuthorization
A — Unified V1One credential, shared. Auth token = fetch token (GitHub→GitHub).Implicit — the source answers "may they?" by returning 404. No ACL to maintain.
B — SplitLogin credential (e.g. Google) grants no source access; the source needs its own service credential.Explicit — must re-introduce a permission check (ACL / group lookup), the machinery Pattern A lets us delete.

Decision (V1): one adapter implements both interfaces. GitHubAdapter realizes OAuthProvider and DocSource (and optionally ReviewStore) as a single cohesive unit sharing one credential internally — the honest expression of "in this case they're the same thing." The interfaces stay separate so a future split case (Pattern B) can implement them as different objects, but we don't pay any abstraction tax to model the common case.

Two cheap guardrails keep this from foreclosing Pattern B: the Worker treats Credential as opaque (carries it provider → session → source, never inspects it), and the credential is audience-tagged (e.g. audience: "github.com") so a DocSource can reject a credential it doesn't accept — turning a miswire into a typed error rather than a confusing 401. DocSource's real contract is therefore "given a credential, may this doc be read — and if so, return it": Pattern A answers both halves in one fetch; Pattern B would answer the "may?" half explicitly. Authorization lives inside the source either way, which is honest — authz is a property of the source, not of the login.

Deployer configures one provider. A deployment selects a single OAuthProvider (GitHub for V1) and the matching DocSource — in practice the same GitHubAdapter instance. Whether more than one provider can coexist, and full Pattern-B support, are open questions; V1 assumes exactly one unified integration.

Deliverable 1 — proxy + auth

Goal: the proxy with auth works as we expect. A reviewer hits a doc URL, logs in via GitHub once, and the Worker renders any branch's doc as that user — with GitHub's 404 acting as the access gate. No review UI yet; the rendered doc is the vanilla htmldocs file. This is the milestone that de-risks the whole idea: it proves auth, the intersection-based authz, and "any branch" rendering end to end.

A. Auth — OAuthProvider (GitHub OAuth + session)

  • If no valid session cookie: OAuthProvider.beginLogin returns the GitHub authorize URL plus a freshly minted, single-use state — the OAuth CSRF nonce. The Worker stashes state in a short-lived cookie and redirects. On return, /auth/callback calls completeLogin(code, state), which verifies state matches and exchanges code + client secret for a user-to-server token.
  • Token storage (decided): keep the GitHub token + refresh token server-side in the session record (DO/D1), keyed by an opaque session id. The cookie carries only that id — HttpOnly; Secure; SameSite=Lax. This gives revocation (delete the record) and keeps the token out of the browser.
  • With token expiration enabled, refresh swaps the 8h token using the 6-month refresh token transparently; on refresh failure, re-login.
  • The provider declares its own redirect target(s) (e.g. /auth/callback); the Worker mounts whatever the configured provider exposes rather than hardcoding GitHub's routes.
  • App-JWT signing (RS256 via Web Crypto) is not needed for D1 — it's only for installation-level calls (PR write-back), which is a follow-up. gotcha when we get there GitHub's key is PKCS#1; importKey wants PKCS#8 (openssl pkcs8 -topk8 -nocrypt).

B. Proxy fetch — DocSource (render any branch, as the user)

Parse the URL into (repo, branch, path) — owner comes from deployment config, see routing — and DocSource.fetchDoc fetches with the viewer's token: 

GET /repos/{owner}/{repo}/contents/{path}?ref={branch}
Authorization: Bearer <user-to-server token>
Accept: application/vnd.github.raw+json
  • 200 → stream the HTML onward. 404 → neutral "not found or no access" page. Do not distinguish 404-missing from 404-forbidden — that's the non-leaking behavior we want.
  • ?ref={branch} delivers "any branch" with no per-branch infrastructure. ref also accepts a tag or commit SHA.
  • Contents API returns raw bytes up to ~100 MB with the raw Accept header; htmldocs files are tiny.

C. Routing & the owner question

(Your question — owner is per-deployment.) owner is deployment config, not part of every URL. A deployment configures one owner (or a small allow-list), so the public URL is just docs.your-org.dev/{repo}/{branch}/{path}. Supporting multiple owners is a config list, not a code change.

  • GET /{repo}/{branch}/{path...} — render a doc (auth → fetch). Owner injected from config.
  • GET /auth/login, GET /auth/callback — provider-declared OAuth routes.
  • Optional GET /{repo} — generated index of renderable docs (discovery; can slip to D2).
D1 done when: a logged-in user renders a doc from a branch in a repo they can access (200), gets the neutral page for a repo they can't (404), and the same URL works across arbitrary branches — all with the token held server-side and refreshed transparently.

Deliverable 2 — review mode

Builds on a proven D1. Adds the two review pieces: inject the comment UI into the served HTML, and persist comments via the ReviewStore. This is where the hosted experience reaches parity with the local serve.sh review mode.

A. Inject — review UI via HTMLRewriter

HTMLRewriter is a streaming, zero-copy HTML transformer built into the Workers runtime — the hosted analogue of what serve.sh does locally. Append the review-mode script + inline CSS to body, passing { html: true } so the string is parsed as markup: 

new HTMLRewriter()
  .on('body', { element(el) { el.append(REVIEW_UI_HTML, { html: true }); } })
  .transform(upstreamResponse)

The injected script renders comment threads, lets the user anchor a comment to an element, and calls the Worker's comment API. Seed it with existing comments — inlined as a <script type="application/json"> blob during rewrite, or fetched on load.

B. Store — ReviewStore

The GitHub App has no storage; the Worker provides it. Recommended: a Durable Object per document for coordination, backed by D1 for queryable comment data.

OptionRoleWhy
Durable ObjectOne per doc path; serializes writes to that doc's threadsStrongly consistent, single-threaded → race-free concurrent comments. SQLite-backed DOs run on the free plan.
D1 (SQLite)Comments table queried by doc id / author / statusRelational queries, GA. Index on doc id to keep rows-read (the billing unit) low.
KV—avoid Eventually consistent (~60s); comments would appear late.

POST /api/comments and GET /api/comments?doc=… back the injected UI. Comments are keyed by a doc identity (source, repo, ref, path) so the store stays source-agnostic.

D2 done when: a reviewer on a rendered doc can leave an anchored comment, another reviewer sees it, and threads persist across reloads — matching local review mode, but org-wide and access-gated.

Setting this up for an org

A one-time setup by an org admin. After this, every repo in the org is reviewable through the Worker with no per-repo configuration.

Goal: agent-driven install. Steps 1–3 should be scriptable so an agent can do them on the user's behalf. The lever is GitHub's App Manifest flow: we generate a manifest with all permissions/callbacks pre-filled, hand the user a single click-through link, and GitHub creates the App and returns the credentials — which a helper script then writes straight into Worker secrets. Plan to ship an install prompt + helper script alongside the Worker.

1. Create a GitHub App (owned by the org)

A GitHub App is the identity the Worker uses to talk to GitHub. Created via the manifest flow with:

SettingValue
Callback URLhttps://docs.your-org.dev/auth/callback (the provider-declared route)
Request user authorization (OAuth) during installationEnabled — the user-to-server flow
Expire user authorization tokensrecommended Enabled — 8h token + 6-month refresh token
WebhookOptional; enable later for proactive session invalidation
Repository permission: ContentsRead-only — to fetch doc files (all D1 needs)
Repository permission: Pull requestsRead & write follow-up only if mirroring reviews to PRs

GitHub issues a Client ID, Client Secret, and a downloadable private key. Keep the permission set minimal — Contents: read-only is enough for D1; everything else is opt-in.

2. Install the App across the org

Install on the org and choose All repositories (or a selected set). Installation defines the ceiling of what the Worker can ever touch; the per-user token then narrows that to what each viewer can personally see (the intersection — see confirmed facts). "All repos" is what makes the system org-wide with zero per-repo work.

3. Deploy the Worker & point a hostname at it

(Your question — where the Worker lives.) The Worker is a deployable app, not skill content, so it lives in its own top-level directory: apps/htmldoc-review/ (its own wrangler.toml). Deploy it and bind a route such as docs.your-org.dev/*. Store the App credentials as Worker secrets — never in source or wrangler.toml (the helper script does this): 

wrangler secret put GITHUB_APP_CLIENT_ID
wrangler secret put GITHUB_APP_CLIENT_SECRET
wrangler secret put GITHUB_APP_PRIVATE_KEY      # only when PR write-back lands; PKCS#8
wrangler secret put SESSION_SIGNING_KEY         # for signing session cookies
# config (not secret): DOC_OWNER=your-org      # the per-deployment owner

Provision storage bindings (Durable Object namespace + D1) in wrangler.toml — D1 needs them; the sessions table is shared with D2's comments store. That's the whole install: one App, one Worker, one hostname.

4. How a reviewer uses it

A reviewer visits https://docs.your-org.dev/{repo}/{branch}/{path-to-doc}.html — e.g. a link dropped in a PR. First visit sends them through GitHub login once; after that, any doc in any repo they can access renders instantly. Repos they can't access return a neutral "not found or no access" page. (Review UI arrives with D2.)

Confirmed facts & assumptions

From web-grounded research (2026-06-29); items below are doc-confirmed unless flagged.

ClaimStatus
Intersection semantics — a user-to-server token grants access to the intersection of (App's installed permissions) ∩ (the user's own GitHub permissions). An org-wide Contents:read App fetched with Alice's token returns only the repos Alice can personally see; others return 404. This is the linchpin of the whole design. confirmed by GitHub docs. Worth a 30-min live sanity check (Spike 1).
GitHub App user-to-server tokens expire in 8h with a 6-month refresh token, when token expiration is enabled (configurable). confirmed
HTMLRewriter can inject a <script>/CSS into upstream HTML via append/prepend with { html: true }; streaming, zero-copy. confirmed. Exact streaming-content signature (Response/ReadableStream as content) verify.
Durable Objects: strongly consistent, single-threaded per object; SQLite-backed DOs available on the free plan. D1 is GA. confirmed. Exact per-object storage limits & pricing verify (they drift).
Contents API ?ref= selects any branch/tag/SHA; raw bytes to ~100 MB with raw Accept header. confirmed
Rate limits: user tokens 5,000/hr (15,000 on Enterprise Cloud); installation tokens scale to ~12,500/hr. confirmed. Caching the proxied HTML at the edge keeps us well under.
Worker private-key signing (RS256) needs PKCS#8; GitHub ships PKCS#1. confirmed (community-corroborated). One-time openssl conversion.

De-risking spikes

The first two are the path to Deliverable 1; the third belongs to D2.

  1. Intersection sanity check (~30 min). Install the App on two repos; get a user token for someone with access to repo A but not B; confirm the Contents API returns 200 for A and 404 for B. Confirms the linchpin live. do first
  2. D1 end-to-end spike (~½ day). OAuth dance → server-side session → authenticated Contents fetch by ?ref → serve the raw doc. Proves auth + intersection authz + any-branch in one shot. No injection yet.
  3. D2 comment store spike. One Durable Object per doc path: write/read a thread with a resolved/open flag through the ReviewStore interface. Decide D1 vs DO-only for the comment data.

Follow-ups (post-V1)

Deliberately out of scope for D1/D2, but designed-for so we don't paint ourselves in. Tracked, not forgotten.

  • GitHub-native reviews, as the user. Because we hold the viewer's token, the ReviewStore could post/reply to GitHub reviews as that user (not a bot). Shape: D1 stays the source of truth, with a GitHub reflector behind the same ReviewStore interface. Interesting and feasible; post-V1. (Recall the constraints in D2 store — commit comments can't thread/resolve; PR review comments need an open PR.)
  • Generic review client. Extract the local serve.sh review UI into a shared client usable by both local serve and the Worker, rather than maintaining two. Sequence after the D2 basics work.
  • PR summary mirroring. Write a resolved-thread summary back to the PR. Drives whether the App needs Pull requests: write and the App-JWT signing path. Hold, don't forget.
  • Second DocSource. GitLab / Bitbucket / raw bucket — the reason the abstractions exist. No work now; the seam is the deliverable.

Decisions & open questions

What's settled vs. what still needs a call. decided items are agreed and reflected in the plan above; open items still need resolution (most are safely deferred past V1).

Decided

  • decided Skip Cloudflare Access. The Worker runs its own OAuth so it directly holds the user token the proxy fetch needs; Access would convey identity only. caveat still verify before production that Access truly can't forward the IdP token (see the reminder banner) — confident enough to start without it.
  • decided Token storage. GitHub token + refresh token live server-side in the session record; the cookie holds only an opaque session id (HttpOnly; Secure; SameSite=Lax). Settled in D1 · Auth.
  • decided One adapter implements both OAuthProvider + DocSource over a shared, audience-tagged credential (Pattern A). Recorded in Abstractions · coupling.
  • decided Two deliverables. D1 = proxy + auth; D2 = review mode. ReviewStore is out of scope for D1 and provisional until D2.
  • decided owner is per-deployment config, not in the URL — see routing. Worker lives in apps/htmldoc-review/.
  • decided Edge caching out of scope for V1. Live fetch is safest given revocation; only revisit if resolveCommit makes a SHA-keyed cache a near-free one-liner.

Still open

  • open One auth provider, or several? V1 assumes exactly one OAuthProvider per deployment. Whether multiple can coexist (and how the Worker routes between them) is undecided — defer until a second provider is real.
  • open Full Pattern-B (split auth/source) support. Structurally left open by the separate interfaces, but it re-introduces an explicit authz step we don't build for GitHub — design only when a real split case appears.
  • open (D2) Comment anchoring. Element id (stable; htmldocs gives articles ids) vs text/DOM-range offset. The existing review mode has an answer — settle it when the generic review-client work happens.
