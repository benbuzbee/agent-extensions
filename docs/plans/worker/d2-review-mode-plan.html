Overview & goal

Deliverable 1 shipped: a per-org Cloudflare Worker logs a viewer in via a GitHub App and serves any repo's .html doc as that user, with GitHub's 404 acting as the access gate — see the proxy-layer doc (how Deliverable 1 works), the app README (deploy), and the D1 handoff (what shipped, live status); its plan is the architecture doc. Deliverable 2 adds the review layer: inject a comment UI into the served doc, persist comments in a store the Worker owns, and give an agent a first-class way to read and resolve those comments over HTTP, so the hosted experience reaches parity with (and in one way exceeds) the htmldocs skill's existing local serve.sh review mode.

The three things this deliverable must produce:

  • A reviewer, on a rendered doc, can select anywhere in the document (not just inside an <article>), leave an anchored comment, and see it persist across reloads and across users.
  • An agent, holding a GitHub token, can GET the comments on a doc and resolve a comment by id — the hosted equivalent of the local sidecar workflow.
  • Comments show real author names, captured from GitHub at login.

The original architecture plan (htmldoc_worker_review.html § "Deliverable 2") sketched this with a Durable-Object-per-doc store and an injected widget. This plan chooses Cloudflare D1 for the store (see below) and specifies the agent API and identity capture the architecture sketch left open.

Removing the article-only limit

Today a reviewer can only comment on a selection that intersects an <article>. That sounds like an anchoring constraint but isn't: the local review architecture shows the encoder already records intersected article ids as pure metadata (anchor.sections) and the decoder "always searches the full document and uses prefix/suffix as the disambiguator." The restriction is solely a UI gate in ui.ts: the selection popover only appears when the selection intersects at least one <article>.

Plan: drop the gate so the popover appears for any non-empty selection in the doc body. Concretely:

  • Replace the "intersects an <article>" predicate with a minimal one (non-collapsed selection, within the rendered doc, not inside the widget's own UI).
  • anchor.sections stays — now legitimately empty for out-of-article selections (the schema already allows an empty array; it's documented as "empty if no article was touched"). No schema change.
  • Because the widget is shared, this immediately improves local review mode too — a wanted side effect, called out so it's not a surprise in the htmldocs skill.
Watch: dropping the gate means selections can land in chrome the doc author didn't expect (nav, footers, code blocks). The anchor still resolves by text, so persistence is fine, but verify the highlight renders sanely across block/inline boundaries and that selecting inside the injected widget UI itself is excluded. One spike during the widget extraction.

The comment store — Cloudflare D1

Deliverable 1 deliberately used only Workers KV (no SQL, no Durable Objects) to stay minimal. Comments need a real store, so this is a genuine step up. The priorities that drive the choice: keep it simple and cheap, one database, and know the cost as data accumulates over time. DB design — queries, schema, migrations

The store choice — one shared Cloudflare D1 database — is already decided above. This section is the design of that database: what it's queried for, its shape, and how we change it later. The schema here is the concern of exactly one thing: the D1Store adapter behind ICommentsStore. The widget and the agent both talk to the granular ICommentsStore (list / create / resolve / reopen / edit / batch); the hosted deployment wires in D1Store while the local server wires in LocalFileStore (a server-only JSON file — the agent never reads it off disk). Nothing outside the D1Store adapter knows these columns exist.

Naming: the store seam is ICommentsStore, with D1Store (hosted) and LocalFileStore (local, server-only JSON) adapters — keep these names consistent in code.

Expected queries

The store only ever answers a handful of shapes. Designing the columns and indexes around exactly these keeps it honest and cheap.

#WhenQueryNotes
Q1 Doc paints; agent reads feedback SELECT … FROM comments WHERE repo = ? AND ref = ? AND path = ? ORDER BY created_at The hot path. Backs GET …?comments and the inline seed. Must hit an index — this is the one query that runs on every doc load.
Q2 Author or agent resolves UPDATE comments SET resolved_at = ? WHERE id = ? Primary-key lookup. Backs the resolve op (see comment API).
Q3 Reviewer posts INSERT INTO comments (…) VALUES (…) Server mints id, stamps author_* from the session, stamps created_at.
Q4 Agent or author purges a thread DELETE FROM comments WHERE id = ? Primary-key delete. Backs the v1 delete op — a genuine hard purge, distinct from resolve's soft-close. See comment API.

The ref rule (decided). A comment is scoped to (repo, ref, path). ref stores the literal value the reviewer was viewing:

  • If a branch was requested (?ref=main), the comment stores "main" and thereby moves with the branch — it shows on whatever main points at now. This is intended.
  • If a commit SHA was requested, the comment stores that SHA and pins to it.
  • If no ref was given, we store the literal string 'default' — never an empty string, never NULL. Q1 then queries ref = 'default' for a no-ref view. Using a real sentinel (rather than '') keeps the column unambiguous in the index and in logs, and makes "the default view" a value you can grep for.
Store returns literal, API decides display. Whether a SHA view should also surface ref = 'default' (or branch) comments is a display-policy question decided in the API layer, not here — the store faithfully returns rows for the exact ref asked. Tracked in Open questions → "Comment identity vs ref."

Proposed schema (schema_version = 1)

CREATE TABLE comments (
  id           TEXT PRIMARY KEY,               -- server-minted uuid
  repo         TEXT NOT NULL,                  -- e.g. "internal-automation"
  ref          TEXT NOT NULL DEFAULT 'default',-- branch/tag/sha; 'default' == no ref requested
  path         TEXT NOT NULL,                  -- doc path within the repo
  anchor       TEXT NOT NULL,                  -- JSON: {sections, prefix, exact, suffix}
  body         TEXT NOT NULL,
  author_login TEXT NOT NULL,                  -- GitHub login, from the session (snapshot)
  author_name  TEXT,                           -- display name, from the session (nullable, snapshot)
  author_id    INTEGER NOT NULL,               -- stable GitHub numeric id, captured now; NOT resolved at render
  created_at   INTEGER NOT NULL,               -- epoch-ms; the same number crosses JSON unchanged (no ISO)
  resolved_at  INTEGER                         -- nullable epoch-ms; NULL == open
);

-- Covers Q1 exactly (repo, ref, path) and keeps the per-load list an index scan.
CREATE INDEX idx_comments_doc ON comments (repo, ref, path);

Notes on the shape:

  • anchor is the same W3C TextQuoteSelector triple the local widget already serializes ({sections, prefix, exact, suffix}), stored as an opaque JSON blob — the widget's payload crosses the wire unchanged. The DB never parses it; anchoring stays entirely client-side.
  • author_login / author_name / author_id are stamped server-side from the session (see Capturing reviewer identity). author_name is nullable because older sessions may lack a display name; author_login and the stable numeric author_id are always present. author_id is captured now (cheap, future-proofs reconciling a renamed user) but is not resolved at render — display uses the snapshotted name/login.
  • resolved_at is the epoch-ms timestamp backing the v1 resolve/reopen ops — NULL = open, a timestamp = resolved. (Hard delete removes the row entirely rather than stamping this column.)
  • No schema_version column on rows. The version lives with the migration set (see below), not per-row; a single tiny table doesn't need per-row versioning.
Confirm — route and store share the 'default' ref sentinel: a missing ?ref= is stored as the literal 'default'. The doc route normalizes a missing ref to the repo default branch, so the doc route and the store must agree on the same sentinel (or normalize in one place) so they never disagree.

Migrations

We adopt Wrangler's built-in D1 migration system from day one, so every schema change is a version-controlled, replayable SQL file rather than an ad-hoc wrangler d1 execute. This is the piece Deliverable 1 never needed (KV has no schema); it's new operational surface, so we set it up deliberately.

Mechanism. A migrations/ directory of sequentially numbered .sql files (0001_create_comments.sql, …). Wrangler tracks which have run in a d1_migrations table inside the database, so each file applies exactly once, in order.

The v1 table above lands as 0001_create_comments.sql. Authoring a migration is the usual scaffold-and-edit loop — wrangler d1 migrations create <db-name> "create comments table", then fill in the generated .sql. Applying them is not a decision an operator makes by hand: it happens on every deploy, automatically. The expandable below is the full deploy-and-vendor story.

When migrations run — deploy & vendor model

When they run. On every deploy.sh run. The deploy script owns applying migrations to production; a schema change reaches the live database as a side effect of shipping, not as a separate gated step an operator has to remember. Concretely, deploy.sh grows two additions, each mirroring an existing idempotent step:

  1. A create-once step cloning the KV-namespace step: guard on the REPLACE_WITH_D1_DATABASE_ID placeholder in wrangler.toml, run wrangler d1 create <db-name> exactly once, parse the returned database id (a UUID — 36 chars with hyphens, unlike the 32-hex KV id format) and sed it into wrangler.toml.
  2. An apply-every-deploy step after the final wrangler deploy: wrangler d1 migrations apply <db-name> --remote. No guard — it is a no-op when nothing is pending. 
# step 2-style: create the D1 database ONCE, wire its id into wrangler.toml
if grep -q "REPLACE_WITH_D1_DATABASE_ID" wrangler.toml; then
  CREATE_OUT="$(npx wrangler d1 create "$DB_NAME")"
  D1_ID="$(printf '%s\n' "$CREATE_OUT" \
    | grep -oE '[0-9a-f-]{36}' | head -n1)"   # UUID, not the 32-hex KV format
  sed -i.bak "s/REPLACE_WITH_D1_DATABASE_ID/$D1_ID/" wrangler.toml && rm -f wrangler.toml.bak
fi

# step 7-style: after the final deploy, apply any pending migrations to prod.
# Unconditional — wrangler computes the delta and no-ops if nothing is pending.
npx wrangler d1 migrations apply "$DB_NAME" --remote

This also lands a [[d1_databases]] block in wrangler.toml (binding, database_name, database_id = "REPLACE_WITH_D1_DATABASE_ID"), replacing the config's current line that forbids adding one.

Why always-apply is safe. migrations apply --remote is idempotent. Wrangler keeps a d1_migrations tracking table inside the database, diffs it against the local migrations/ folder, and runs only the unapplied files, in order. In a non-interactive shell (our script) it skips the confirmation prompt but still captures a backup first; a failed migration rolls back, leaving the last successful state applied. So deploy.sh never has to detect whether a migration is pending — it always calls apply and lets wrangler compute the delta, exactly matching the script's existing guarded/idempotent philosophy.

Local vs. remote. Tests and local dev apply with --local against miniflare's local SQLite; production uses --remote, and deploy.sh only ever runs --remote. A local apply never touches production.

How it fits the vendor/deploy upgrade loop. vendor.sh copies the whole app root except an explicit excludes list (deps, build output, local secrets, wrangler state, wrangler.toml); migrations/ is not excluded, so migration files are vendored like any other source. wrangler.toml is operator-owned — a re-vendor never overwrites it, dropping the fresh template beside it as wrangler.toml.upstream for a manual diff/merge — so the operator's database_id survives. The whole operator upgrade story is therefore the copy-and-deploy loop already documented in PROVENANCE.md: re-run vendor.sh from newer upstream → new migrations/NNNN_*.sql files land → re-run deploy.sh → migrations apply --remote sees them as unapplied and runs only those. The operator never decides "do I need to migrate."

Adding a column safely — the common future case (e.g. an agent_authored flag, a severity):

  1. New migration: ALTER TABLE comments ADD COLUMN <name> <type> as nullable (or with a default) so existing rows stay valid. This is the whole change for a plain additive column.
  2. Apply --local, confirm, then --remote.

Anything harder than an additive column — changing a type, adding NOT NULL to an existing column — is constrained by SQLite's limited ALTER TABLE. Use the expand → backfill → contract pattern: add the new nullable column; dual-write and backfill existing rows in batches (one-off script or Worker); switch reads to the new column; optionally drop the old column in a later migration. We don't need this for v1; it's documented so the first person who does isn't surprised.

Aging out — Cloudflare D1 has no TTL. There is no built-in row TTL or auto-expiry — no analog to Workers KV's per-key expirationTtl. Any expiry is manual: a Worker on a Cron Trigger running a scheduled DELETE FROM comments WHERE created_at < ? (with created_at indexed to keep the scan cheap; each deleted row bills as one row-written). Decision: skip it for now. Comments are tiny text rows and the free tier's storage / row-read / row-write allowances are effectively unlimited for a small team, so aging-out is a data-hygiene choice, not a cost necessity — we defer building cron cleanup until volume warrants it. One caveat on file: a D1 database at its storage cap can reject writes — including the DELETEs you'd use to clean up — so at real scale we'd want a cleanup strategy in place before getting large, not after.

Capturing reviewer identity

Comments need author names. Today the session record holds only tokens; Deliverable 1's completeLogin never asks GitHub who the user is. Plan: after the token exchange, call GET /user once with the fresh token and store { login, name, id } on the session KV record alongside the tokens. When a comment is created, the API stamps author_login/author_name from the session — the browser never supplies its own identity, so it can't spoof another reviewer.

  • One extra GitHub call per login only (never per request); identity is cached on the session for its lifetime.
  • Keep it minimal — login, display name, numeric id. No email, no avatar in v1. The numeric id is the stable key: logins can be renamed on GitHub, so id is what we'd match on if we ever reconcile.
  • The record carries a version field (see below) so this and any later identity fields can evolve without a flag day.

For the agent, identity comes from its GitHub token the same way — the access probe in Authorization already calls GitHub as the agent — so agent-authored actions are attributable too. Relevant if an agent ever creates comments; v1 grants it read + resolve/reopen + delete, not create.

Names are a snapshot, not a live join

author_login/author_name/author_id are copied onto the comment row at create time, and rendering uses the snapshotted author_name/author_login — never a live lookup. That's deliberate — it keeps read/list a single indexed query with no fan-out to GitHub. The stable author_id is captured for future reconciliation but is not resolved at render. One known consequence, called out so it isn't a surprise:

Known limitation, with the data captured early. If a reviewer later changes their GitHub display name (or login), already-stored comments keep the old name — because rendering reads the snapshotted author_name/author_login, never a live lookup, so read/list stays a single indexed query with no fan-out to GitHub. Decision: capture author_id on the comment row now, but do not resolve it at render. Storing the stable numeric author_id at create time costs nothing and preserves the ability to reconcile a renamed user's old comments later; deliberately not doing a render-time name resolution keeps v1's read path a single query. So v1 gets the data-capture for free and defers only the extra lookup.

Existing sessions when identity becomes required

Deliverable 1 shipped live, so there are already valid session records in KV that predate this field. They must not break, and we need a deliberate answer for them rather than discovering it in production.

KV values are opaque blobs with no enforced schema: adding { login, name, id } to the record shape leaves every existing record physically unchanged, so a naive read of an old session simply finds those fields absent. Two ways to handle that:

ApproachWhat happens to existing sessionsCost
Lazy on-read upgrade chosen On the next authenticated request, if the record lacks identity, call GET /user with the session's stored token, write { login, name, id } + bump version back to the same key. Old sessions silently self-heal; nobody is logged out. One extra GitHub call the first time each stale session is used, then cached.
Forced re-login Invalidate all sessions so everyone re-authenticates through the normal completeLogin path. The lever is an iat cutoff: set SESSION_VALID_SINCE (a ms timestamp in wrangler.toml [vars]) to "now" and redeploy; getValidAccessToken deletes-on-read any record whose login-time iat predates the cutoff. Bumping the KV namespace is a cruder alternative. See the session writer. Every current user is logged out once.

Decision: lazy on-read upgrade. We already hold each session's token server-side, so identity is derivable for a live session without bothering the user — the on-read GET /user is the same call completeLogin will now make, just deferred. Forced re-login is the fallback only if a future required field can't be derived from what the session already holds (e.g. something the token can't fetch); for identity it can, so we take the graceful path.

To make this and future changes routine, the session record gains an explicit version field now (identity capture ships as version: 2; pre-identity records are treated as version: 1). Read logic branches on version, upgrades in place, and writes the record back — the standard KV schema-evolution pattern. That keeps every later session-shape change a lazy upgrade instead of a migration event. (There's no bulk backfill job: sessions are short-lived under their native TTL, so any record that's never read again simply ages out.)

One writer for the session record

Decision: every write path — new login, token refresh, and lazy identity backfill — goes through a single persist() chokepoint in session.ts, the only constructor of a SessionData. Callers hand it a token Grant (plus, optionally, a fresher identity); they never hand-build the record. That one writer enforces the schema and fixes each field's provenance: stamped fields are re-set on every write (version); pinned fields are set once at login and carried unchanged forever (iat, the login instant in ms, and identity); supplied fields arrive fresh from GitHub on each write (the access_token / refresh_token / expires_at triple). A single writer keeps these from drifting apart across the three call sites.

Pinning iat is the crux: persist() mints it via prior?.iat ?? Date.now(), so a refresh carries the login-time value forward untouched. A refresh must never bump it — otherwise an active user would silently dodge any age-based cutoff by simply staying logged in. That enables a cheap forced-re-login lever: a SESSION_VALID_SINCE config value (a ms timestamp in wrangler.toml [vars]). getValidAccessToken deletes-on-read any record whose iat predates it and returns null — already the universal "send them through login" signal, so no new logout path is added. To log everyone out, bump the var to "now" and redeploy: idempotent, no KV enumeration, no cron. The same pinned iat also leaves room for a future rolling max-session-age if ever wanted.

iat and version stay orthogonal: version tracks record shape (schema evolution → the lazy in-place upgrade above), iat tracks grant validity and age (time-based invalidation). Neither overloads the other. The sketch below is the intended structure, to be verified against the exact arctic field extraction, config plumbing, and TTL handling at implementation time.

Session-writer sketch — single chokepoint (verify at runtime) 
const CURRENT_VERSION = 2;

interface Grant {
  access_token: string;
  refresh_token: string;
  expires_at: number;   // ms
  refresh_ttl: number;  // seconds, for KV expirationTtl
}

interface SessionData {
  version: number;              // stamped:  re-set every write
  iat: number;                  // pinned:   login instant (ms), minted once then carried
  identity: Identity | null;    // pinned:   carried unless a caller supplies a fresher one
  access_token: string;         // supplied: fresh from GitHub each write
  refresh_token: string;        // supplied
  expires_at: number;           // supplied: ms
}

// The ONLY writer of a session record. `prior` is the record being replaced
// (null = brand-new login). iat is pinned here — minted on a null prior, carried
// otherwise — so a refresh cannot bump it past a cutoff. identity is likewise
// carried unless a caller supplies a fresher one.
async function persist(store, id, grant: Grant, prior: SessionData | null, identity?: Identity): Promise<SessionData> {
  const data: SessionData = {
    version: CURRENT_VERSION,                       // stamped every write
    iat: prior?.iat ?? Date.now(),                  // pinned: minted once, then carried
    identity: identity ?? prior?.identity ?? null,  // pinned/carried
    access_token: grant.access_token,               // supplied fresh
    refresh_token: grant.refresh_token,
    expires_at: grant.expires_at,
  };
  await store.put(id, data, grant.refresh_ttl);
  return data;
}

// login:   persist(store, id, grant, null, identity)
// refresh: persist(store, id, grantFromArctic(tokens), s)
// upgrade: persist(store, id, grantFrom(s), s, fetchedIdentity)

async function getValidAccessToken(cfg, store, id, forceRefresh = false) {
  const s = await store.get(id);
  if (!s) return null;
  if (s.iat < cfg.session_valid_since) { await store.delete(id); return null; }  // forced re-login
  if (!forceRefresh && Date.now() < s.expires_at - SKEW_MS) return s.access_token;
  return doRefresh(cfg, store, id, s);   // whole record, so refresh carries pinned fields
}
Decision. The session record carries an explicit version field (identity capture = version: 2, pre-identity = version: 1) rather than relying on a plain presence check. The explicit version keeps later session-shape changes clean, and a missing/older version simply triggers a backfill on next refresh.
Note — this is KV, not Cloudflare D1. The versioning above is for the session records in KV. The comments live in Cloudflare D1, whose schema changes go through Wrangler's migrations directory (numbered .sql files, applied --local then --remote, tracked in d1_migrations); additive columns are added nullable. The two stores evolve by different mechanisms — don't conflate them.

We log reviewer identity, on purpose

Reviewer login and display name are logged with comment operations, for auditability.

The reasoning: this Worker is installed into a single org and is operated by someone who can already see the org's members and everything they can read. A public GitHub login and display name are not sensitive PII in that context — the operator can see them in GitHub directly. Suppressing them from logs buys no meaningful privacy while actively costing us the ability to answer "who left / resolved this comment, and when" from operational logs. Auditability wins.

Concretely:

  • Comment create/resolve log lines include the acting author_login (and name where handy) alongside the existing sessionId, the doc (repo, ref, path), and the outcome. Resolve is the one worth auditing most — it's the agent's primary mutation and closes out a raised issue.
  • Tokens, refresh tokens, and the raw session record are still never logged. "Log identity" means the public GitHub login/name, not the credential — the token-secrecy posture from Deliverable 1 is unchanged.
  • Identity still lives only in the server-side session record and in Cloudflare D1, never in the cookie (cookie stays the opaque session id). Logging identity doesn't change where it's stored.

The comment API (human + agent)

What exists today is a local workflow that writes a JSON sidecar file to disk. The hosted surface generalizes that into one HTTP API on the Worker, and — the key move — the agent always speaks HTTP too. The agent is simply handed the right URL: a local URL when a local server is serving the doc, the Worker URL when it is hosted, the same call shape either way. Decision: the on-disk JSON sidecar is no longer an agent-facing artifact. Behind the local URL a local server still persists to a JSON file, but only the server touches that file — it is an implementation detail of the LocalFileStore, not something the agent reads off disk. Two consumers share this one surface: the injected widget (browser session cookie) and the agent (GitHub bearer token). Every operation enforces the access probe.

Tracked for deletion. The old "agent reads the sidecar JSON off disk" path is superseded by HTTP-only access and is tracked for removal — the agent obtains comments only through the HTTP surface described here, never by opening a file.

The surface has one shape: the URL names the collection, the body names the operation. The sections below give the route, the op envelope, batch, and the store interface behind them.

The comments API, in one shape

The comment surface is body-ops over one collection URL. The URL names only the collection — the doc whose comments these are — and carries no verb and no thread id: 

# Hosted Worker — the URL carries <repo> (the org's repos)
GET    /<repo>/<doc>?ref=<ref>&comments      → list every thread on this doc
POST   /<repo>/<doc>?ref=<ref>&comments      → apply one op, or a batch of ops

# Local server — NO <repo> segment (it serves a file tree, not an org's repos)
GET    /<doc>?ref=<ref>&comments             → same shape, doc path + optional ?ref
POST   /<doc>?ref=<ref>&comments             → same op/batch body

Only the hosted Worker URL names a <repo>; the local server serves a file tree, so its route is the doc path plus ?ref and &comments, no repo segment. The op envelope, the batch shape, and the DocKey the store sees are otherwise identical — the difference lives only in how each runtime parses its URL into that opaque doc key.

Decision: the query string names the collection; the body names the operation. chosen A single request body is one op object {op:"create"|"reply"|"resolve"|"reopen"|"delete"|"edit", …}; a batch body is a JSON array of those same objects, mixing verbs freely. The resource marker is a bare valueless ?comments (?comments=1 accepted as an equivalent), and every verb and id travels in the body. Batch therefore falls out for free: the array form is the singular form repeated, with per-op results returned in request order. There is no &thread and no &op in the URL.

Two consumers share this one surface — the injected widget (browser session cookie) and the agent (GitHub bearer token) — and every request, single or batch, first clears the access probe for (repo, ref, path) once, before any op runs.

This shape rests on standard URL semantics: the query string is orthogonal to the path, so ?comments can never collide with a repo file path. That orthogonality is a design property to confirm in the router spike, not an asserted GitHub behavior. The catch-all router gains one branch: if the query string carries the bare key comments, dispatch to the comment handler with the already-parsed (repo, ref, path); otherwise serve the doc. A missing ?ref= normalizes to the 'default' sentinel exactly as the doc route and store already agree.

// OpResult — a DISCRIMINATED UNION: discriminate first on `ok`, then on `op`, so a single
// op returns its own verb-specific payload. One success arm PER VERB (reply/edit reserved),
// which is exactly what lets a batch collect one array of mixed, type-safe results — every
// per-op result object, including a reserved edit's {ok:true, op:"edit", comment}, is assignable.
type OpResult =

  | { ok: true;  op: "reply";              comment:  Comment }    // reserved
  | { ok: true;  op: "edit";               comment:  Comment }    // reserved
  | { ok: true;  op: "resolve" | "reopen"; thread:   Thread }
  | { ok: true;  op: "delete";             threadId: ThreadId }   // v1: hard purge
  | { ok: false; op: Op["op"];             error:    OpError };

Validation happens before any store call. The Worker validates the request envelope with Zod (importing from zod/mini) and a safeParse-style check; a malformed envelope is rejected with a 400 before the store is touched. The anchor is validated for shape only — a well-formed TextQuoteSelector — never for whether it actually matches text in the doc; that DOM/semantic match is explicitly out of scope because the Worker streams HTML through HTMLRewriter and never builds a DOM.

Status codes. 404 (neutral, from the access probe) for any caller who cannot fetch the doc — comments never leak a doc's existence. 400 for a malformed envelope (unknown op, missing required field) before any store call. 200 for a single op that succeeded; 207 Multi-Status for a batch (which may contain per-op failures — Layer C). 404 for a single op naming a threadId/commentId that does not exist on this doc.

The URL names the collection only. Because the verb and every id live in the body, the URL is identical for list, create, reply, resolve, reopen, edit, and batch. Nothing in the query string ever changes shape as the verb set grows — a new verb is a new op value, not a new route or a new query key.

Envelope validation — Zod (zod/mini), anchor shape, and what is out of scope

Validator: Zod 4, imported from zod/mini. The zod/mini entry point is the tree-shakable, functional API that keeps only the schemas actually referenced in the bundle — the right choice on Workers, where bundle size is a real constraint. It is confirmed Workers-compatible. A safeParse-style call validates the request envelope at the route chokepoint, and a malformed envelope is rejected with 400 before any store call: an unknown op, a missing required field for that verb, a wrong-typed field, or (for a batch) a body that is not an array of op objects. Nothing reaches ICommentsStore until the envelope parses.

The anchor is validated for shape only. The schema for create requires a well-formed TextQuoteSelector: exact is a required string; prefix and suffix are optional strings; sections is an optional string array. That is the whole anchor contract the Worker enforces.

What is explicitly out of scope: DOM/semantic anchor matching. The Worker cannot confirm that an anchor actually matches text in the doc, because it streams the HTML through HTMLRewriter and never builds a DOM — there is no document to search for the quote. So the Worker validates that the anchor is well-shaped, and stops there; whether the quote still resolves against the live document is a client-side concern. Orphaned anchors (the quoted text edited away under a moved branch ref) therefore remain a handled client concern — the widget re-anchors by prefix/exact/suffix at render time and degrades gracefully — not something the Worker can or does check.

Unit-tested. The envelope validator has direct unit tests: each verb's required/optional fields, the unknown-op and non-array-batch rejections, and the anchor-shape schema (accepting a minimal {exact}, accepting the full prefix/exact/suffix/sections form, rejecting a missing exact or a non-string field) — all asserting a clean 400 with no store interaction.

Layer C — batch: an array of ops, per-op results, partial-failure & idempotency

A batch request is a JSON array of the exact op objects from Layer B, mixing verbs freely, POSTed to the same collection URL. It exists to let the agent close many threads (or a mix of resolve + reply) in one round trip. 

// batch body — an array, verbs mixed freely
[ { "op": "resolve", "threadId": "c-1a2b" },
  { "op": "resolve", "threadId": "c-3c4d" },
  { "op": "reply",   "threadId": "c-5e6f", "text": "addressed in edit" } ]

Response shape. 207 Multi-Status with one result per input op, in request order. Each result also echoes its own thread id (in thread on success, in error.threadId on failure), so the agent correlates results to the ops it sent by id rather than relying on array position:

{ "results": [
    { "ok": true,  "op": "resolve", "thread": { /* updated Thread */ } },
    { "ok": true,  "op": "resolve", "thread": { /* updated Thread */ } },
    { "ok": false, "op": "reply",   "error": { "code": "not_found", "threadId": "c-5e6f" } }
] }

Decision: a batch is best-effort per-op, never all-or-nothing. Each op in the array is attempted independently, in order, and a failing op (a threadId that does not exist, a constraint violation, a thread another request concurrently deleted) reports its own error and does not roll back the ops that already succeeded. There is no wrapping transaction across ops in either store (see Layer D) — this is the deliberate mechanism that keeps a single stale thread id from silently discarding an agent's other 20 resolves. The whole request is rejected up front with 400 only for envelope-level problems the router catches before touching the store (not an array, an element with an unknown op, a missing required field), and with 404 if the access probe fails for the doc.

Idempotency. resolve and reopen are naturally idempotent — resolving an already-resolved thread returns ok:true with the current (already-set) resolvedAt, no error and no second timestamp overwrite. edit is idempotent on an identical patch by the same rule: an identical body re-stamps nothing. create and reply are not intrinsically idempotent (each mints a new id); a client that must retry a batch safely sends the optional per-op clientOpId from Layer B, which the server dedupes within a short window. clientOpId is optional and off the critical path — v1 ships without the dedupe store and leans on resolve/reopen idempotency, which covers the agent's cleanup role.

Verb set — mirror GitHub's names, own the store

We borrow GitHub's verb names but run our own store. GitHub's comment model is the reference for vocabulary and structure; the store (Cloudflare D1) is ours, for the reasons below.

We borrow GitHub's verb names but run our own store (Cloudflare D1). This is not a rejection of "don't reinvent the wheel" — it's the opposite. The research is decisive that native GitHub comment storage does not fit rendered-HTML review:

  • GitHub has no anchor primitive for a rendered-HTML text range. Native anchors are diff line, commit position, or none — a W3C TextQuoteSelector (the widget's prefix/exact/suffix triple) maps to none of them. Stored natively, the anchor is an opaque blob we would have to re-anchor ourselves anyway, so "no store to run" is illusory the moment arbitrary-HTML anchoring is required.
  • The only native surface with both resolve and threaded reply is PR review threads, which require an open PR ({pull_number} in every write path). Manufacturing a throwaway PR per doc/ref to host comments would be absurd. resolveReviewThread/unresolveReviewThread are GraphQL-only and PR-bound; commit comments are flat (no reply, no resolve); issue/PR-conversation comments are flat (hide/minimize, no resolve); discussions can thread but have no resolve. No native surface offers the combination review mode needs without a PR.
  • Native storage would also mean posting as the user, dragging OAuth scopes and REST rate limits through every comment read, with state scattered and no clean per-(repo, ref, path) query.

Thread-owns-resolution, one-level replies. We copy GitHub's structural model, not just its verb names. From the research: in GitHub a thread is the resolvable container and resolution lives on the thread, not the comment (PullRequestReviewThread.isResolved); replies are one level only ("replies to replies not supported"). We adopt both:

  • A thread is the unit an anchor attaches to and the unit that resolves. The immutable TextQuoteSelector anchor lives on the thread root; (repo, ref, path) indexes the thread. Resolution is a property of the thread (resolved_at on the root), never of an individual reply.

This means the schema evolves from "row = comment" toward "row = thread root, with replies referencing it." For v1, where reply/edit/delete are deferred, a single-comment thread and a bare comment are indistinguishable, so the existing comments table stands; the forward-compatible move is to treat each existing row as a thread root and add a nullable reply_to (thread-root id) column when reply lands. resolved_at is already reserved on the row and now formally means thread resolution.

Resolve and delete, both in v1. resolve is the default soft-close — it keeps the audit trail, matches GitHub's own bias (PR threads resolve; they are not deleted in the review flow), and is reversible via reopen; it is the agent's cleanup role. delete is a genuine hard purge by threadId: the row is gone, no audit trail, no reopen. The two are distinct tools with distinct intent — soft-close for "addressed, keep the history," hard delete for "remove this entirely" — and both are part of the v1 verb set.

Batch is first-class. This is a designed part of the v1 API, not a maybe — it is exactly what lets an agent close many threads (or mix resolve + reply) in one round trip without a single stale id rolling back the rest. No native GitHub equivalent is mirrored here; batch is a property of our own body-op shape.

Authorization — the access probe

The linchpin: a caller must be able to see the doc before they can touch its comments. Comments must never become a side channel that leaks a private doc's existence or content to someone who couldn't fetch the doc itself. So every comment operation reuses Deliverable 1's authorization model: can this caller fetch this doc as themselves?

  1. Resolve the caller's GitHub token — from the session cookie (widget) or the bearer header (agent).
  2. Probe: issue a GitHub Contents read for (repo, ref, path) with that token. We only need the status line, never the body.
  3. If the probe is not 200 (or 304 on a re-probe — see below) → return the same neutral 404 the doc route returns. Comment endpoints are thus indistinguishable from "no such doc" for anyone lacking access — no existence leak, identical to Deliverable 1's contract.
  4. If 200/304 → the caller can see the doc, so they may read/write its comments. Proceed.

Cloudflare Workers ship no Express-style middleware layer; the idiomatic "run on every route" equivalent is either a single dispatch inside fetch() or a router library (Hono / itty-router) whose use('*', …) registers a before-every-route handler. Deliverable 1 already routes through one catch-all dispatch — a switch over the three /auth/* routes, then everything else is a doc request — and the ?comments action layers onto that same catch-all. So both authenticated branches (serve-doc and comments) already funnel through a single point, right after the session/bearer token is resolved.

Decision: one checkAccess helper invoked at that single post-auth chokepoint chosen — not a router library. The probe is factored into one checkAccess(cfg, store, token, repo, ref, path) call placed before the request forks into serveDoc vs. the comment handler. Because there is exactly one place a caller becomes authenticated and checkAccess owns it, the probe cannot be forgotten when a future comment verb is added: it is structural, not a convention each handler must remember. A deny — both GitHub 403 and 404 mean no-access — maps to the shared neutral 404 (deny semantics), so comment endpoints stay indistinguishable from "no such doc."

Adopting Hono or itty-router is not warranted here: it adds a dependency and a second routing model to guarantee something one call at one chokepoint already guarantees, and the route set is tiny (three auth routes plus the catch-all). Revisit a router only if the route surface grows substantially.

Probe mechanics & checkAccess shape

The "access probe" is Deliverable 1's fetch-as-user check, narrowed to metadata. The doc route resolves the caller's token (session cookie for the widget, bearer header for the agent), then issues a GitHub Contents read for (repo, ref, path) with that token and inspects only the status line. See the probe request and bytes vs. quota for the media-type and ETag details. Helper shape — one call site downstream of token resolution, one deny mapping: 

type Access =
  | { ok: true }
  | { ok: false; denialResponse: Response };   // always neutral() — no existence leak

async function checkAccess(
  cfg: Config,
  store: KvSessionStore,
  token: string,
  repo: string,
  ref: string | undefined,
  path: string,
): Promise<Access> {
  const status = await probeContents(cfg, token, repo, path, ref); // object+json, status only
  // 200/304 => visible; 403 AND 404 (and anything else) => deny
  return status === 200 || status === 304
    ? { ok: true }
    : { ok: false, denialResponse: neutral() };
}

// inside fetch(), after the /auth/* switch and token resolution — the single chokepoint:
const access = await checkAccess(cfg, store, token, repo, ref, docPath);
if (!access.ok) return access.denialResponse;   // guards BOTH branches below
return url.searchParams.has("comments")
  ? handleComments(cfg, store, req, repo, ref, docPath, token)
  : serveDoc(cfg, store, url, sessionId, token, repo, docPath, ref);

The 401-refresh-retry loop stays inside serveDoc as it is today; checkAccess is purely the visibility gate, and the two concerns compose without either handler re-implementing the probe.

The probe request: metadata, not the file body

Deliverable 1's fetchDoc streams the whole file (Accept: application/vnd.github.raw+json) because it needs the bytes to serve the doc. A probe needs only the status line, so it should ask GitHub for the cheapest representation: 

GET /repos/{owner}/{repo}/contents/{path}?ref={ref}
Accept: application/vnd.github.object+json
Authorization: Bearer {caller-token}

object+json returns a small metadata JSON (name/path/sha/size/type/_links) rather than the file body. Compared to the alternatives on the same endpoint:

  • raw+json (what fetchDoc uses today) streams the full body.
  • the default vnd.github+json returns the body base64-encoded in a content field (~1.33× the raw size).
  • object+json is the fewest-bytes representation.

The byte win is largest on big files. The probe never reads content regardless — it inspects only the HTTP status. Same endpoint, same token, same status semantics as fetchDoc; only the representation shrinks.

Open decision: the research qualifies that for files ≤ 1 MB the object response may still inline content, so the byte saving on small docs (most planning HTMLs) is modest — the big win is on large files. The swap is still worth it (it's free to ask for object, and the probe never reads the body), but confirm you're not expecting a large saving on typical docs before treating this as the headline benefit.
On HEAD: there is no documented HEAD on the Contents endpoint, so we do not rely on it as an authz signal. The "transfer fewer bytes" win here is a media-type swap (object+json), not a method change.

Bytes / CPU yes object+json reduces payload (and parse work) on every probe. Always a win.
Rate-limit quota no Method and Accept header do not change primary-quota cost. Every GET/metadata call is 1 request against the 5,000/hr core pool. Swapping to object+json saves bytes, not quota.

The only documented way to make a repeat probe free against primary quota is a conditional request. Persist the ETag returned by the first probe of a path@ref and send If-None-Match on subsequent probes: 

GET /repos/{owner}/{repo}/contents/{path}?ref={ref}
Accept: application/vnd.github.object+json
Authorization: Bearer {caller-token}
If-None-Match: "{stored-etag}"

A 304 Not Modified (unchanged and still authorized) does not count against the primary rate limit. So a 304 is treated exactly like 200 for the visibility decision — access is confirmed, quota untouched. Note GET /rate_limit is also free against primary quota but cannot substitute for this check: it carries no per-path access signal.

Open decision: the ETag cache must be keyed by (path@ref@token-identity), not by path@ref alone — otherwise one user's stored ETag could yield a 304 that authorizes a different caller who never had access. Confirm token-identity is part of the cache key before this lands.

Deny semantics and non-leak

Both 403 and 404 occur for no-access, and both map to deny → we return the neutral 404. Only 200 (or 304 on a re-probe) counts as access. Changing the Accept header or adding If-None-Match does not change who can read what — it is the same endpoint, token, and status semantics as fetchDoc. The non-leak contract is preserved unchanged.

Cost & race notes. A probe adds one GitHub Contents call per request or batch (unless it resolves to a free 304) — not per op. Every op in a batch shares the same (repo, ref, path) doc key the URL names, so checkAccess runs once at the route chokepoint before any op executes and the whole batch rides that single probe. Comment requests are rare — human pace, agent in bursts — so the 5,000/hr core limit is not a concern in practice. Two levers keep it that way if it ever bites: (1) conditional re-probes (above) give free 304s on unchanged path@ref; (2) an optional short-TTL probe cache keyed by (session/token-identity, repo, ref, path) skips the network call entirely within the TTL. verify keep the TTL short so revoked access is re-checked promptly — the cache trades a small staleness window for zero calls. The probe authorizes visibility, not authorship: resolving someone else's comment is allowed — resolve authority equals the visibility the probe already grants (any viewer of the doc may resolve; see the Locked decisions).

Two review paths now exist: the more mature local one (the htmldocs skill's serve.ts Node server + src/comments/ widget, writing JSON sidecars to disk) and the hosted one this deliverable builds (the Worker + Cloudflare D1). What we share: all of the UX, one store interface

The review UX is one body of code — every pixel and every interaction — shared by both runtimes so the two review experiences cannot drift. The chosen store interface

Decision: a granular ICommentsStore, not a coarse full-model save. chosen Granular write methods map 1:1 to the op envelope, are the cleanest thing to unit-test (one method, one row change, one assertion), and make batch() a natural first-class member rather than a diff engine bolted onto save. A coarse save(model) would force every store to re-derive "what changed" and drag whole-file last-writer-wins back into a design the per-op shape exists to avoid. 

interface ICommentsStore {
  list   (doc: DocKey): Promise<Thread[]>;
  create (doc: DocKey, op: CreateOp,  author: Author): Promise<Thread>;
  reply  (doc: DocKey, op: ReplyOp,   author: Author): Promise<Comment>;   // reserved
  resolve(doc: DocKey, op: ResolveOp, author: Author): Promise<Thread>;
  reopen (doc: DocKey, op: ReopenOp,  author: Author): Promise<Thread>;
  delete (doc: DocKey, op: DeleteOp,  author: Author): Promise<ThreadId>;  // hard purge
  edit   (doc: DocKey, op: EditOp,    author: Author): Promise<Comment>;   // reserved
  batch  (doc: DocKey, ops: Op[],     author: Author): Promise<OpResult[]>;
}

// One OpResult per op in a batch, in request order. It is a DISCRIMINATED UNION:
// discriminate first on `ok`, then on `op`, so a single op carries its own
// verb-specific payload — the type-safe mixed array a batch returns. Same union
// the single-op POST returns (see #api). `reply`/`edit` arms are reserved.
type OpResult =
  | { ok: true;  op: "create";             thread:   Thread }
  | { ok: true;  op: "reply";              comment:  Comment }   // reserved
  | { ok: true;  op: "resolve" | "reopen"; thread:   Thread }
  | { ok: true;  op: "delete";             threadId: ThreadId }  // v1: hard purge
  | { ok: true;  op: "edit";               comment:  Comment }   // reserved
  | { ok: false; op: Op["op"];             error:    OpError };

Each write method takes the exact op object the route parsed, plus the server-stamped Author (from the session or the agent token — never from the body, so identity can't be spoofed). DocKey is the opaque (repo, ref, path) tuple the collection URL already carries — locally it resolves under --root, hosted it is the D1 key, and making it opaque is what lets one widget serve both worlds. Five members (create/reply/resolve/reopen/edit) correspond 1:1 to envelope op values (create / reply / resolve / reopen / delete / edit, with reply/edit reserved); list is the GET. batch is implemented in terms of those single-op methods: it loops the ops in order, calls each op's own single-op method independently, and collects one OpResult per op (best-effort — a failing op records its error and the loop continues). Because OpResult discriminates first on ok and then on op, a batch returns one array of mixed, verb-specific, type-safe results. Two implementations sit behind the interface: D1Store (SQL) and LocalFileStore (server-only JSON file; the agent never touches it).

Per-method impl in D1Store vs. LocalFileStore; batch loops the single-op methods
MethodD1Store (SQL)LocalFileStore (server-only JSON, read-modify-write)

Batch is implemented in terms of the single-op methods, in both stores. There is no separate batch code path and no wrapping transaction: batch simply iterates the array, dispatches each op to its own single-op store method, and appends that method's result (or its caught error) to the ordered OpResult[]. That yields the Layer-C contract for free — ordered results, best-effort per-op (a failed or stale op never rolls back the ops that already ran), resolve/reopen/edit idempotent — and it is identical for both stores because it is the same loop over the same methods.

LocalFileStore does a read+write per op inside that loop, and that is accepted for v1. A ten-op batch is ten read-modify-write cycles on the one JSON file. At the local single-user, human-or-agent pace this is a non-issue, and reusing the exact single-op methods keeps the code trivially correct. A load-once / save-once optimization (fold every op into one in-memory model, persist once) is possible later behind the same OpResult[] contract, but it is not needed now and is deliberately not built. D1Store has no analogous concern — each single-op method is its own statement, committed as it runs. The only observable difference between the stores is a durability window under a mid-run crash, invisible in the response.

Error handling — useful without leaking

A store method that can't complete surfaces an OpError that the widget turns into a modal message. The widget shows a minimal set of messages that are useful to a reviewer without leaking anything about the doc, the repo, or the caller's credentials. Decision: three user-facing messages, and the modal never surfaces repo existence, GitHub status codes, or tokens. v1 A denial and a genuine 404 collapse to the same generic message — the modal never distinguishes "you don't have access" from "it doesn't exist," preserving the neutral-404 non-leak contract all the way to the UI.

The modal message set + what an OpError never carries
SituationWhat the modal showsNever shown
Access probe fails — denial or genuine 404 (indistinguishable, by design) "You don't have access to this doc, or it doesn't exist." Which of the two it was; whether the repo/doc exists; the GitHub 403/404.
Transient save failure (store write errored, network blip, D1 unavailable) "Couldn't save your comment — try again." The underlying error, the store type, any stack or status code.
Stale id — a threadId/commentId resolved/reopened/edited that no longer exists "This comment no longer exists." Anything beyond "gone" — no repo/doc context, no id provenance.

The rule. An OpError carries only a coarse code (no_access — the merged denial/404 — · transient · not_found) plus the op and, for not_found, the offending id so the widget can drop that thread from the view. It never carries repo existence, a GitHub status code, a token, or the raw store error. The neutral-404 gate lives server-side (the access probe), so a no_access op result is the only access signal that ever reaches the browser, and it says nothing a denied caller couldn't already infer. Server logs still record the real cause (with reviewer identity, per the logging decision); the reviewer-facing modal is the redacted view.

Injection — shared at the contract, split at the mechanism

Both runtimes inject basically the same thing: an inline JSON seed of existing comments (so the page paints with its comments and zero extra round trips) plus the <script type="module"> widget tag. Decision: shared seed/tag helpers (the what), per-runtime injector (the how) — not a shared injector, not a fork. chosen One pair of shared helpers — seedJsonScript(model) and widgetScriptTag() — produces the exact HTML to inject (both pure functions of the shared CommentsModel). Each runtime keeps only the thin injector that places those strings.

  • Local: serve.ts string-splices the two helper outputs before </body> on files it reads off disk (today's injectIntoHtml).
  • Hosted: the Worker wraps the Deliverable 1 doc response in HTMLRewriter and appends the same two nodes to <body>, on a 200 HTML response only — the neutral 404 path is untouched (no widget, no leak).
new HTMLRewriter()
  .on('body', { element(el) {
    el.append(seedJsonScript(model), { html: true });
    el.append(widgetScriptTag(), { html: true });
  }})
  .transform(docResponse)
Why the injector itself doesn't unify

HTMLRewriter is a streaming per-element callback — it never holds the whole document and exposes append/prepend/after with { html: true }, not string indexing — whereas serve.ts operates on the full in-memory string. Any "shared injector" abstraction would collapse to (model) => [seedJsonScript(model), widgetScriptTag()], which is exactly the shared helpers; the placement step has no honest common form. So the line sits at the emitted string: shared code decides what markup and guarantees the escaping/contract once, each runtime owns the ~10 lines that decide where it lands.

Watch: the escaping (< → &lt; inside the <script type="application/json"> seed, so a comment body can't break out with a </script>) and the seed id/type live in the shared helpers, not in either injector. If a runtime hand-rolls the <script> string it silently reopens that breakout hole and the widget's boot-time sniff. Both injectors must call seedJsonScript/widgetScriptTag, never inline the markup.

One genuinely-open item remains; the rest are settled in Locked decisions.

  • decided Resolve UX — keep it simple for v1. Decision: resolving a thread just changes its comment indicator color to green (instead of the default color) to signal resolved — no hide/toggle machinery and no reopen affordance in the v1 UX. Resolve keeps the row, so the data is all there; the display stays minimal. The UX can be expanded later (a "show resolved" toggle, a reopen affordance) without a schema change. (The API still exposes reopen as an op — see the op envelope — this decision is only about the v1 widget affordance.)
  • open Probe caching. The access probe adds one GitHub Contents call per comment request. Comment ops are rare — and a batch POST is one request that clears the probe once for many ops (batch is first-class), so it already cuts per-op probe pressure — so the 5,000/hr core limit isn't a concern. If bursty agent runs ever bite, add a short-TTL per-(caller, repo, ref, path) probe cache (on top of the free 304 conditional re-probe). Left as a documented lever, not built in v1. See Authorization.
