Document scope

The htmldoc-review app is, at its core, a Cloudflare Worker that proxies HTML documentation and layers collaboration on top of it — chiefly sharability and reviewability. The proxy takes security seriously: it can never widen the scope of access. Because a GitHub-hosted doc is fetched with the viewer's own access token, each person sees only what they are already authorized to see, and a file they cannot reach returns a neutral 404 rather than leaking its existence. The aim is simply to make HTML documents easy to share and review together, so they can serve as durable, high-quality context for agentic engineering.

This document covers the shipped proxy layer (Deliverable 1): the GitHub App login, the as-the-user fetch, session handling and silent token refresh, the non-leak property, and the code layout — enough for a maintainer to extend or debug it. It does not cover review mode, the comment UI and its storage, which is Deliverable 2 and lives in its own future doc (d2-review-mode-plan.html). A forward-looking rationale doc (htmldoc_worker_review.html) explores the wider design; where it and this doc disagree, the running code wins. Setup and operations are only summarized here, with full detail in the app README and the D1 handoff.

What it does

A single Cloudflare Worker fronts one GitHub account — GitHub's term for an entity that owns repos, either an organization account (e.g. myboop-ai) or an individual user account (e.g. benbuzbee). The account is fixed per deployment as REPO_ORG. A viewer requests https://<host>/{repo}/{path}?ref=<branch|tag|sha>; the Worker logs them in via a GitHub App OAuth flow, then fetches the requested file from the GitHub Contents API using that viewer's own token and serves it back.

The one insight. Because the fetch runs as the viewer, GitHub itself is the authorization engine. We never maintain a permission list: a repo or file the viewer can't see simply returns 404, which the Worker passes through as a neutral "not found or no access" page — so access control and existence-hiding both come for free from the same fetch. Authentication and authorization collapse into one call.

  • The Worker and the GitHub App operate at the same level — the account (the org). A repo within it is selected by the first path segment and the doc path is the remainder; the commit/branch/tag is the ?ref= query param (omit it for the repo's default branch). The account is never in the URL. So /app-ios/docs/foo.html?ref=main means repo app-ios, doc docs/foo.html, on main.
  • Login is not a one-time event. The viewer signs in once interactively, but the Worker re-authenticates whenever GitHub rejects the token: an expired access token is refreshed silently, and a 401 mid-fetch forces one refresh-and-retry before falling back to a fresh login.
  • Self-hosted, per-account: each account creates its own GitHub App and runs its own Worker; we never hold anyone's secret.
  • Sessions in Workers KV with native TTL — no Durable Object, no SQL. The browser cookie holds only an opaque session id.

Security principles

The proxy layer holds to a small set of security invariants. Each is stated plainly below with a concrete example of how the code upholds it. Treat these as invariants: a change that breaks one is a regression even if every test still passes.

  • Never widen access. The proxy can only return what the viewer's own GitHub token can already fetch; it holds no elevated credential of its own for reading docs. Example: fetchDoc calls the GitHub Contents API with the logged-in user's user-to-server token in the Authorization header, so a repo they cannot see on GitHub is equally unreachable through the proxy.
  • Don't leak existence. Missing, forbidden, and malformed-path cases all return the same neutral 404 with a byte-identical body, Not found or no access. Example: a GitHub 404 (missing) and a 403 (forbidden) both fall through to neutral(), so a viewer cannot tell whether a private doc exists.
  • Keep secrets off the client. Tokens live server-side in Workers KV; the browser cookie carries only an opaque session id, set HttpOnly, Secure, SameSite=Lax. A stolen cookie yields no GitHub token, and revocation is simply deleting the server-side record.
  • Never log secrets. No access or refresh token, OAuth code, client secret, signing key, or Authorization header is ever logged. Example: the OAuth rejection path logs a fixed reason string and status only; success logs carry the opaque sessionId and nothing more.
  • Verify the callback is genuine. The OAuth callback is authenticated with a signed state: a random nonce HMAC-signed with a server-side STATE_SIGNING_KEY, stored in a short-lived HttpOnly cookie and echoed as the OAuth state. A forged callback cannot produce a valid signature, and the spent state cookie is burned on every callback.
  • Treat request paths as hostile. Repo and path segments are validated (empty, ., and .. are rejected) then percent-encoded, so ?, #, &, and .. cannot traverse out of the configured org/repo or inject query params such as an overridden ref.
  • No secrets in source. Real secrets are pushed at deploy time via wrangler secret put; the repo carries only fake placeholder values in .dev.vars.example.

Request lifecycle

Every request enters one fetch handler (worker/index.ts), which dispatches on the URL path: the three /auth/* routes are auth plumbing, and everything else is treated as a doc request. A doc request with no valid session is bounced to login; with a session, it parses the path and fetches.

The auth parts — App, token, refresh

Three pieces cooperate: a GitHub App (the identity), the Worker (which runs the OAuth flow and holds the tokens server-side), and the Contents API (fetched with the viewer's token). The App issues a short-lived user-to-server access token plus a long-lived refresh token; the Worker stores both in KV and presents the access token when fetching docs, silently refreshing it when it expires.

The login itself is a GitHub App user-to-server OAuth flow, run via the arctic library in core/oauth.ts. CSRF is hand-rolled with a signed state: beginLogin mints a random nonce, HMAC-signs it with STATE_SIGNING_KEY, stashes nonce.sig in a short-lived HttpOnly cookie, and sends the bare nonce as the OAuth state. On callback, completeLogin recomputes the HMAC over the cookie's nonce and requires it to match both its own signature and the returned state — a forged callback can't produce a valid signature without the server-side key.

Sessions & token refresh

Sessions live in Workers KV (core/session.ts over the SessionStore seam, implemented by worker/kv-store.ts). The record is { access_token, refresh_token, expires_at }, keyed by a single crypto.randomUUID() (CSPRNG, 122 bits — clears the OWASP session-id floor). The cookie carries only that id; both tokens stay server-side, so revocation is "delete the record" and a stolen cookie yields no GitHub token.

ConcernHow it's handled
ExpiryAccess token treated as expired 30s before its real expiry (SKEW_MS) so it can't lapse in flight. getValidAccessToken returns the cached token if fresh, else refreshes.
Silent refreshdoRefresh swaps the refresh token for a new access token (GitHub rotates the refresh token, so the new one is persisted). KV TTL is set from refresh_token_expires_in (default 180d).
Dead grantA rejected refresh (revoked/expired) purges the session → forces re-login. A network error does NOT purge — it surfaces as 5xx so a transient blip can't log everyone out.
Refresh raceNo Durable Object to serialize refreshes, so two concurrent requests can both refresh; the first rotates the token and the second's looks dead. On a dead grant we re-read once: if a concurrent request already rotated to a fresh token, use it instead of purging. A residual race remains and is accepted for D1.

On a doc fetch, a 401 from GitHub (token stale/revoked mid-flight) triggers exactly one forced refresh + retry in serveDoc; a second 401 or a dead session bounces to login. This is the single place the 401→refresh→retry path lives, so the happy path and re-auth path can't diverge.

Fetching docs

core/docsource.ts parses the path and fetches the raw file. parseDocRequest splits the URL into { repo, docPath } (first segment = repo, rest = doc path); fetchDoc calls GET /repos/{REPO_ORG}/{repo}/contents/{path} with Authorization: Bearer <user token> and Accept: application/vnd.github.raw+json, which returns the file's raw bytes (the proxy serves them back with a text/html content type). A present ?ref= is percent-encoded (so slashed branches like feature/a/b survive); an absent one is omitted so GitHub serves the repo default branch — no default_branch lookup needed.

The response mapping is where two security principles live: fetchDoc collapses GitHub's 404 (missing) and 403 (forbidden) — plus unparseable paths and unsafe segments (., .., empty) via InvalidPathError — into one byte-identical neutral() response, and safeSegments validates and percent-encodes each path segment so it can't escape the REPO_ORG/repo confinement or inject a query param. Both are load-bearing: changing either is a regression, not an improvement.

Code structure

The Worker is built around a deliberate split: a portable core that knows nothing about Cloudflare, and a thin Cloudflare layer wrapped around it. The core is written against Web-standard globals only (fetch and Web Crypto), so it can run anywhere those exist. The Worker entry point acts as the composition root: it reads Cloudflare Env bindings and hands the core a plain Config object, which means core code never imports a Cloudflare type. That boundary is also the seam where a future non-GitHub documentation source would slot in.

DirectoryWhat lives there
src/core/ The portable core with no Cloudflare dependencies: the OAuth flow, session lifecycle, the as-the-user doc fetch, cookie handling, and response builders. See oauth.ts, session.ts, docsource.ts.
src/worker/ The Cloudflare-specific layer: the fetch handler and path dispatch (the composition root), the KV-backed session store, and logging setup. See index.ts, kv-store.ts.
test/ Tests that mirror the split. test/core/ runs as plain vitest on Node, while test/worker/ uses vitest-pool-workers with a local fetch-mock. Every GitHub call is mocked, so the suite needs no real credentials.
scripts/setup/ The vendor-then-deploy tooling. See vendor.sh, deploy.sh, create-worker-app.mjs.

Setup, in brief

Full procedure: the app README and D1 handoff. In short — the model is vendor-then-deploy:

  1. Vendor (vendor.sh): copy the app into your own infra repo (it stamps PROVENANCE.md and preserves your wrangler.toml on re-vendor). You configure and deploy from your copy, never the upstream template.
  2. Deploy (deploy.sh, idempotent, deploy-first): set REPO_ORG, then it deploys once to learn the workers.dev URL, derives CALLBACK_URL, creates the GitHub App via the manifest flow with that callback baked in, pushes secrets, and redeploys.
  3. Install the App on your org (required — creating ≠ installing; the script prints the URL).
