Overview

User asks the agent to open a doc in review mode. The agent runs the review server (node dist/serve.mjs) in the background and hands User a localhost URL. User opens it, selects text in the doc body, clicks the Comment button that appears, and writes a note. The note is saved over the doc's ?comments HTTP API and persisted to a JSON sidecar under the server's sidecar directory. On its next pass the agent drives that same ?comments API — list, resolve, delete — and addresses each comment via HTML edits. The sidecar file is an on-disk backup, not the interface.

Components

dist/serve.mjs

The agent's entry into review mode — the review-server CLI, invoked as node dist/serve.mjs [target]. It resolves the served root from a positional file-or-directory target (a file serves its parent folder and points the URL at the file; a directory serves its whole tree), auto-probes a free port in 8000–8099, binds 127.0.0.1, and prints the two-line URL: / SIDECAR_DIR: stdout contract after a successful bind. Either target makes every .html under the served folder reviewable. --sidecar-dir <path> pins the sidecar location for resume; absent it, the server picks an auto-tmp dir and announces it on the SIDECAR_DIR: line. serve.sh beside SKILL.md is a compatibility shim that forwards its arguments straight to dist/serve.mjs. Invocation contract — argument shapes, the two-line stdout, what to hand User — in SKILL.md § Review mode (entry point) and the header comment in serve.ts (flags, port probe, stdout contract).

The widget (dist/comments.mjs)

A single checked-in ESM artifact bundled by esbuild from TypeScript under src/comments/. The server injects it at runtime — pages on disk stay vanilla, with no <script> wiring. The widget mounts only when the inline JSON seed (#__htmldocs_comments) is present; absent seed, the page renders normally. Bootstrap parses the seed ({threads, author}), builds one HttpCommentsStore, and hands it to a shared UX layer (selection popover, <dialog> composer, margin gutter, highlight registration). The widget adopts whatever author the seed carries — it never chooses a runtime or transport.

Styles inject via a constructable CSSStyleSheet on document.adoptedStyleSheets under the --htmldocs-cmt-* prefix, so they cannot collide with the host doc. Highlights register as Range objects in one named registry (htmldocs-cmt) in CSS.highlights — no <mark> wrappers, no DOM rewriting.

HTTP endpoint (GET/POST <doc>?comments)

The one comment transport, shared by the widget and the agent. The doc's own URL names the collection; add ?comments. GET lists every thread ({threads}); POST applies one op (create/resolve/reopen/delete) or a JSON array of them (best-effort batch, 207 with per-op results). The local route is the doc path plus ?comments with no <repo> segment; the hosted Worker URL adds the repo. The path is validated like a static GET: it must resolve under the served root to an .html/.htm file. Behind the local route, SidecarStore does an atomic read-modify-write per op — see § Known friction.

Sidecar JSON

The backing store for the local ?comments route — a durable on-disk backup, not the interface. One JSON file per doc under SIDECAR_DIR, mirroring the doc's root-relative path (sub/bar.html → <SIDECAR_DIR>/sub/bar.comments.json). Multi-doc sessions produce one sidecar per doc that received a save; they never aggregate. The on-disk model is {doc, schema: 2, threads}, where threads is exactly the internal Thread[] — the same shape a GET ?comments returns — so SidecarStore reads and writes it with no format conversion; every layer speaks the one {threads} shape. A file that fails v2 validation loads as empty with a one-line warning.

Agent recipe

Entry point in SKILL.md § Review mode: run node dist/serve.mjs in the background, capture the URL: line, hand it to User. To read and act on comments, drive them through scripts/comments-api.sh (the read/write twin of the review server) — list to read, resolve/delete by thread id to act — rather than raw GET/POST. Full recipe — the one shape, the agent's verbs — in references/comments.md.

Data flow

  1. Inject. The server reads the current sidecar and rewrites the HTML response, inserting the bundle <script> and an inline <script type="application/json" id="__htmldocs_comments"> carrying {threads, author}. The widget sees the seed, mounts, adopts its stylesheet, and registers existing anchors as CSS.highlights — zero network round trips for initial state.
  2. Capture. User selects text in the doc body; the popover surfaces a Comment button. Clicking it encodes the anchor immediately — freezing prefix/exact/suffix against the live DOM — then opens the composer.
  3. Save. Submit POSTs one {op:"create", anchor, text} to <doc>?comments. The server persists it via SidecarStore; the widget appends the returned thread to its highlights and gutter without reloading. A failed op surfaces as an error and renders nothing.
  4. Read-back. On its next turn the agent drives the same API — GET to list, POST a resolve/delete op by thread id — and addresses each comment via HTML edits. Reloading any page re-seeds from disk, so User sees current state. The agent lists, resolves/reopens, and deletes; it does not author comments.

Known friction

  • Two-tab writes are per-op, not transactional (local server only). Each save is a single op the local server applies with a read-modify-write against the sidecar file, so every op lands and two tabs don't clobber each other's whole file. This is per-op no-clobber, not a transaction: no cross-op isolation or locking, so a genuinely concurrent read-modify-write on the same op could still race — fine for single-user localhost review. The hosted Worker doesn't share this friction: its D1 store applies each op as its own checked, doc-scoped SQL statement.
  • Port collisions outside 8000–8099. dist/serve.mjs probes that range and exits if every port is taken. User running 100+ dev servers (or a stale review server per port) needs to free one before review mode will start.
