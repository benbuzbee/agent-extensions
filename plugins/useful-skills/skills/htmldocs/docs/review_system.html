Overview

User asks the agent to open a doc in review mode. The agent runs serve.sh in the background and hands User a localhost URL. User opens it, selects text in the doc body, clicks the Comment button that appears, and writes a note. The note is saved over the doc's ?comments HTTP API and persisted to a JSON sidecar under the server's sidecar directory (auto-tmp by default, or pinned via --sidecar-dir). On its next pass the agent drives that same ?comments API — list, resolve, delete — and addresses each comment via HTML edits. The sidecar file is an on-disk backup, not the interface.

Components

serve.sh

The agent's entry into review mode. A small Bash shim next to SKILL.md that preflights node on PATH, picks a free port in 8000–8099, prints the URL: line, and execs the Node server (dist/serve.mjs) bound to 127.0.0.1. Accepts a file or a directory; either way every .html under the served folder becomes reviewable. Optional --sidecar-dir <path> pins the sidecar location for resume; absent it, the server picks an auto-tmp directory and announces it via the second stdout line (SIDECAR_DIR:). Invocation contract — argument shapes, the two-line stdout, what to hand User — in references/comments.md.

The widget (dist/comments.mjs)

A single ESM artifact (~130 KB, checked in) bundled by esbuild from TypeScript sources under src/comments/. The server injects it at runtime — pages on disk stay vanilla, with no <script> wiring required. The widget mounts only when the inline JSON seed (#__htmldocs_comments) is present in the DOM; absent seed means review mode isn't active and the page renders normally.

Modules:

  • main.ts — bootstrap + runtime select; hands a built store to the shared mount.
  • review-ux/mount.ts — the shared lifecycle (slimmed CommentsWidget): highlight rebuild, re-anchor, save, UI attach, unmount, test-handle wiring. It paints straight from the internal {threads} seed.
  • review-ux/anchor.ts — encode/decode between a DOM Range and the W3C TextQuoteSelector triple (32-char prefix/suffix windows, Hypothesis convention). The encoder also records the ids of every <article> the selection intersects in an anchor.sections array — pure metadata, the decoder always searches the full document and uses prefix/suffix as the disambiguator.
  • review-ux/popover.ts — the selection popover and its selectionInDocBody gate (any selection inside the doc body qualifies, not just inside an <article>).
  • review-ux/composer.ts — the <dialog> body-text composer.
  • review-ux/gutter.ts — margin-gutter thread bubbles, with resolved-state styling.
  • review-ux/highlight.ts — CSS Custom Highlight registration + the injected stylesheet.
  • review-ux/inject.ts — the shared seed/script-tag markup helpers; the internal {threads} seed and its </script>-breakout escaping live here.
  • review-ux/store.ts — the ICommentsStore seam between the shared UX and the adapters.
  • review-ux/types.ts — Anchor, Comment, Thread, the Op envelope, and branded ids. No legacy shape lives here — the legacy disk format is confined to adapters/local/legacy-format.ts.
  • adapters/http-store.ts — HttpCommentsStore, the shared browser HTTP client both runtimes build. Pure fetch transport: it drives every op (create/resolve/reopen/delete, batch) over <doc>?comments, addressing the collection URL derived from location. (The inline JSON seed is parsed by review-ux/mount.ts for the initial paint — the store never touches it.) Each op is one request.

Styles inject via a constructable CSSStyleSheet on document.adoptedStyleSheets with the --htmldocs-cmt-* prefix so they cannot collide with the host doc's tokens. Highlights register as Range objects under one named registry (htmldocs-cmt) in CSS.highlights — no <mark> wrappers, no DOM rewriting.

HTTP endpoint (GET/POST <doc>?comments)

The one comment transport, shared by the widget and the agent. The doc's own URL names the collection; add ?comments. GET lists every thread ({threads}); POST applies one op object (create/resolve/reopen/delete) or a JSON array of them (best-effort batch, 207 with per-op results). The local route carries NO <repo> segment — it is the doc path plus ?comments (the hosted Worker URL adds the repo). The path is validated the same way a static GET is: it must resolve under --root to an .html / .htm file. Behind the route the server's SidecarStore does an atomic read-modify-write of the sidecar per op, so a crash mid-write cannot truncate it and two tabs don't clobber each other's whole-file state — see § Known friction.

Sidecar JSON

The backing store for the local ?comments route and a durable on-disk backup — not the interface. One JSON file per doc, under SIDECAR_DIR, mirroring the doc's root-relative path (overview.html → <SIDECAR_DIR>/overview.comments.json; sub/bar.html → <SIDECAR_DIR>/sub/bar.comments.json). Multi-doc sessions produce one sidecar per doc that received a save; they never aggregate. The legacy *.comments.json (de)serialization — reading the on-disk shape in and writing it back out unchanged (including resolvedAt) — lives only in src/comments/adapters/local/legacy-format.ts, invoked from the SidecarStore; every other layer speaks the internal {threads} shape.

Agent recipe

Entry point lives in SKILL.md § Review mode: run bash <htmldocs-skill>/serve.sh path/to/doc.html in the background, capture the URL: line, hand it to User. To read and act on comments, drive the doc's ?comments API — GET to list, POST to resolve/delete. Full recipe — the one shape, the agent's verbs, orphan handling — in references/comments.md.

Data flow

  1. Inject. The server reads the current sidecar from disk and rewrites the HTML response, inserting the bundle <script> and an inline <script type="application/json" id="__htmldocs_comments"> carrying the sidecar contents. The browser loads the doc; the widget sees the seed, mounts, adopts its stylesheet, and registers existing anchors as CSS.highlights entries — zero network round trips for initial state.
  2. Capture. User selects text inside an <article>. The selection popover surfaces a Comment button. Clicking it calls encodeAnchor(range) immediately — freezing prefix/exact/suffix against the live DOM — then opens a <dialog> composer with the textarea focused.
  3. Save. Submit POSTs one {op:"create", anchor, text} envelope to <doc>?comments. The server applies it via SidecarStore and lands the sidecar atomically under SIDECAR_DIR. The widget appends the returned thread to its highlights and gutter without reloading. A failed op surfaces as an error; nothing is rendered.
  4. Read-back. On the next agent turn the agent drives the same ?comments API — GET to list, POST a resolve/delete op by thread id — and addresses each comment via HTML edits. Reloading any page re-seeds from disk, so User sees the current state. The agent's v1 verbs are list + resolve/reopen + delete (it does not author comments).

Known friction

  • Two-tab writes are per-op, not transactional. Each save is a single op that the server applies with a read-modify-write against the sidecar, so two tabs don't clobber each other's whole file — every op lands. This is per-op no-clobber, not a transaction: there is no cross-op isolation or locking, so a genuinely concurrent read-modify-write on the same op could still race. Fine for single-user localhost review. See plans/review_server_buildout.html § Decisions.
  • Port collisions outside 8000–8099. serve.sh probes that range and exits if every port is taken. User running 100+ dev servers (or a stale serve.sh per port) needs to free one before review mode will start.
