Overview

Let an article embed a diagram by writing Mermaid DSL inside a <pre class="mermaid">, plus a small <script> that loads Mermaid from a CDN and calls mermaid.run(). The file stays a single standalone document: open it anywhere — file://, a browser, a rendered HTML preview — and the diagram draws itself in the page. No server, no build step, no separate render. The DSL stays in the file as the diffable, agent-fluent source.

Why Mermaid. It is the lingua franca of diagrams-as-code, and agents are already fluent in it. Two forces make that true. It's a terse, line-oriented plain-text grammar — closer to writing Markdown than to hand-coding SVG — so a model renders an idea in a handful of tokens. And models have seen a great deal of it: GitHub has displayed ```mermaid blocks as diagrams natively since 2022, so Mermaid source sits as plain text across millions of READMEs, wikis, and issues that these models train on. The upshot is that an agent can emit a correct sequence, state, or flow diagram from memory, with no tool call — which is exactly what makes "write the diagram inline" cheap.

Why agents are fluent in Mermaid — evidence & caveats
  • Training-data saturation. GitHub rendered Mermaid in Markdown natively starting Feb 2022 (Gists shortly after); GitLab earlier still. Mermaid is among the most popular diagram-as-code tools (tens of thousands of GitHub stars, millions of npm downloads/week), so its plain-text source is widespread in corpora.
  • Text-native, expressive grammar. Concise, declarative, line-oriented, Markdown-inspired — token-efficient and sequential, which maps to how LLMs generate text far better than verbose SVG XML or heavier PlantUML.
  • Demonstrated capability. Official AI features exist (Mermaid Chart's AI chat / "repair diagram", a Mermaid GPT, Copilot/Claude integrations) and academic benchmarks (e.g. MermaidSeqBench, MermaidFlow) report high-but-imperfect generation quality.
  • Caveats (represented honestly). Models still emit syntax errors on complex diagrams (hallucinated keywords, stray parentheses), and syntax drifts across versions — Mermaid v11 made flowchart labels Markdown-by-default, breaking some v10 \n usage. This is why we pin a CDN version and why a visible parse-error on open is acceptable feedback.

Sources gathered via gemini web search (flash-vetted; treat quantified figures as approximate). Load-bearing primary: GitHub's Feb-2022 native-rendering announcement (github.blog) and the Mermaid docs (mermaid.js.org). Benchmark papers were not opened — cite only after verifying.

Where it fits: today htmldocs only offers hand-rolled inline <svg> for diagrams — fine for three boxes, painful past that. Inline Mermaid gives the agent a lightweight way to drop a richer sequence, state, or flow diagram straight into a doc.

Core decision & why

We want htmldocs files to stand on their own, and we want diagrams always visible when the file is opened. So when an agent adds a diagram, it injects the lines that load Mermaid and call mermaid.run() directly into the document. The browser renders the diagram on open — no review server, no build step, nothing to run first.

htmldocs prefers self-contained docs; inline Mermaid is the first optional feature that trades a little of that on purpose (see self-contained-files). It adds one external <script> — a pinned CDN import — only in docs that actually contain a diagram, because every alternative that keeps "the diagram always shows" is worse here:

AlternativeWhy not (now)
Build-time bake to static SVGAdds a render CLI + DOM dependency and a re-bake-on-edit step; bloats the file with serialized SVG.
Serve-time injection (review server)Diagrams appear only when viewed through serve.mjs — never on a raw file:// open. Fails "always visible".
Inline Mermaid's full ~MB bundleTruly self-contained and offline, but every diagram doc becomes megabytes.

The cost we knowingly accept: a diagram needs network to render. Offline, the <pre class="mermaid"> simply shows its DSL as text — a readable fallback, and the form an agent reads best anyway. If a fully-offline, portable artifact is ever needed, build-time bake remains the escape hatch (out of scope here).

Consequence for the skill. Instead of a hard "no external JS" rule with a carve-out, htmldocs's self-contained principle is softened to "be mindful of the reading & portability experience" — self-contained by default, with Mermaid the first optional feature that trades a little of it on purpose.

How it works

Two pieces in the file: a <pre class="mermaid"> per diagram, and one Mermaid <script> per document (near </body>). On open, the browser fetches Mermaid from the CDN; mermaid.run() finds every pre.mermaid and replaces it with an inline <svg>.

The actual code is tiny

There is no library to build — the entire "implementation" is the snippet below. It lives in references/mermaid.md for the agent to copy, and in the test fixture to prove it renders. Captured here folded:

The reusable snippet — what ships in the prompt and the tests 
<!-- one per diagram -->
<figure data-kind="diagram">
  <pre class="mermaid">flowchart LR
  A[Source] --> B[Sink]</pre>
</figure>

<!-- one per document, near </body> -->
<script type="module">
  import mermaid from 'https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs';
  const dark = matchMedia('(prefers-color-scheme: dark)').matches;
  mermaid.initialize({ startOnLoad: false, theme: dark ? 'dark' : 'default' });
  await mermaid.run();
</script>

Light/dark theming

Initialize Mermaid with a theme chosen from prefers-color-scheme so diagrams track the doc's light/dark palette like the hand-rolled SVGs already do. The exact init lives in the one-time script snippet — pick theme: 'dark' vs 'default' from matchMedia('(prefers-color-scheme: dark)').

Authoring contract — what an agent writes

A diagram is a <figure> wrapping a <pre class="mermaid"> (the figure is the addressable unit — it gets an id when it's a link or comment target). The agent also ensures the document has the one-time Mermaid script, adding it once if absent. 

<figure id="ingest-sequence" data-kind="diagram">
  <pre class="mermaid">sequenceDiagram
  participant W as Ingest worker
  participant DB as Postgres
  W->>DB: write row
  DB-->>W: ack</pre>
  <figcaption>Ingest path: worker writes before publishing.</figcaption>
</figure>

<!-- once per document, near </body> -->
<script type="module">
  import mermaid from 'https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs';
  const dark = matchMedia('(prefers-color-scheme: dark)').matches;
  mermaid.initialize({ startOnLoad: false, theme: dark ? 'dark' : 'default' });
  await mermaid.run();
</script>

Two htmldocs-specific rules (the Mermaid syntax itself the model already knows):

  • Escape <, >, & inside the <pre>. Mermaid DSL rarely contains them, but a label like Vec<T> must be escaped as htmldocs already requires inside any <pre> — otherwise the doc DOM breaks below that point. The browser decodes the entities back to text before Mermaid reads them, so the rendered label is correct.
  • One script per document, not per figure. mermaid.run() processes every pre.mermaid on the page, so the script block is included once. Multiple diagrams in a doc share it.
