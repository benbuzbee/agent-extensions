What this is

Hosted review 2.0 is the local review widget (review_system.html) lifted onto the org-wide htmldoc-review Cloudflare Worker (the Deliverable 1 proxy layer). The Worker already fronts a GitHub org and serves each private HTML doc by fetching it from the GitHub Contents API as the logged-in viewer, so GitHub itself is the authorization engine. Deliverable 2 adds a durable, multi-user comment layer on top: reviewers comment in the browser, comments persist in Cloudflare D1 (one shared database, migrated from day one via migrations/0001_create_comments.sql), and an agent with a GitHub token can drive the same comment collection over an HTTP API — list a doc's comments, resolve or delete them by id — without ever opening a browser.

The comment store is scoped per (repo, ref, path). Comments carry real GitHub author names (captured server-side from the session, never from the request body). A resolved comment is a soft close: its row is kept, its indicator turns green, and it stays visible — never hidden. A deleted comment is a hard purge by thread id.

Where each store lives. Sessions stay in Workers KV (sess:<id>); comments live in D1. They evolve by different mechanisms — do not conflate them. The agent reaches comments only through the ?comments API below — the same API the local runtime now uses, so there is one agent recipe for both (a local doc keeps a sidecar file on disk as its backing store, but that is not the interface).

The API surface

Comments are body-ops over one collection URL — the doc's own URL with a ?comments marker. There is no separate comment path: 

GET  https://<worker-host>/<repo>/<doc-path>?ref=<ref>&comments
POST https://<worker-host>/<repo>/<doc-path>?ref=<ref>&comments
  • <repo> — the first URL path segment (the org/owner is fixed per Worker via REPO_ORG and is never in the URL). Note: the hosted URL carries a <repo> segment; the LOCAL review server does not — it serves a file tree, not a repo.
  • <doc-path> — the repo-relative path to the .html doc (the URL remainder).
  • ?ref= — optional branch / tag / SHA. Omit it for the repo's default branch. A missing ref is stored and queried as the literal string default (never an empty string or a resolved branch name), so listing and mutating agree on the same collection — just omit ref to target the default branch.
  • &comments — the marker that forks this request from "serve the doc" to "the comment API".

GET returns the doc's full comment set: 

200 { "threads": [ Thread, ... ] }   // ordered by created_at, open AND resolved

A Thread is:

{
  "id":        "<threadId>",
  "anchor":    { "exact": "...", "prefix"?: "...", "suffix"?: "...", "sections"?: ["..."] },
  "root":      { "id": "<commentId>", "author": { "login": "...", "name": "..."|null, "id"?: 0 },
                 "body": "...", "createdAt": 1720000000000 },
  "replies":   [],
  "resolvedAt": 1720000009999 | null      // epoch-ms; null == open, a number == resolved
}
Timestamps are epoch-milliseconds numbers end to end (createdAt, resolvedAt) — never ISO strings on this API. author.id is the stable GitHub numeric id, present on hosted comments. replies is always [] in v1 (threads are single-comment).

Authenticating

Every ?comments request must be authenticated. Two credentials, one gate:

CallerCredentialHeader / cookie
Browser widget (a human reviewer) the Worker session Cookie: sid=<session> (set by the OAuth login; refreshed transparently)
Agent (you) a GitHub token (PAT or installation token) Authorization: Bearer <github-token>

Bearer wins if both are present. The bearer token is used as-is against GitHub — there is no session to refresh. It must be able to read the target doc on GitHub (that is exactly what the access gate below checks). A request with no credential gets an honest 401 {"error":"authentication required"} — uniform across every path, so it leaks nothing about whether the doc exists.

Author attribution. The author on any comment you create is stamped server-side and can never be set from the request body. An agent's bearer-authored mutation is attributed to a distinguishable placeholder {"login":"agent"} (never the generic "unknown"), and agent resolves are audit-logged. Note the v1 rule below: the agent surface is list + resolve/reopen + delete — NOT create.

Operations

POST a single op object, or a JSON array of op objects for a batch. The v1 op set:

opBodyEffectAgent v1?
create{op:"create", anchor:{exact, prefix?, suffix?, sections?}, text, clientOpId?}New anchored threadNo (reviewer-only)
resolve{op:"resolve", threadId}Soft-close: stamp resolvedAt, keep the row, indicator → green, stays visibleYes
reopen{op:"reopen", threadId}Clear resolvedAt (idempotent)Yes
delete{op:"delete", threadId}Hard purge by thread idYes
reply / edit—Envelope-reserved: parsed then rejected 400 {"error":"op not yet supported"}No (reserved)

Single-op responses:

200 { "ok": true, "op": "resolve", "thread": Thread }        // resolve / reopen
200 { "ok": true, "op": "delete",  "threadId": "..." }       // delete
200 { "ok": true, "op": "create",  "thread": Thread }        // create (reviewer)
404 { "ok": false, "op": "resolve", "error": { "code": "not_found", "threadId": "..." } }
400 { "error": "op not yet supported" }                      // a single reserved op
400 { "error": "<why>" }                                    // malformed envelope (BEFORE any store write)

Batch (a JSON array) is best-effort per op — no cross-op transaction — and always returns 207 with results in request order: 

POST [ {op:"resolve", threadId:"a"}, {op:"resolve", threadId:"ghost"}, {op:"delete", threadId:"b"} ]
207 { "results": [
       { "ok": true,  "op": "resolve", "thread": {...} },
       { "ok": false, "op": "resolve", "error": { "code": "not_found", "threadId": "ghost" } },
       { "ok": true,  "op": "delete",  "threadId": "b" }
] }
Batch clears the access probe once. The gate probes GitHub exactly once per request, so a batch of N ops pays one probe, not N. Prefer a batch when you have several ops for the same doc.

Agent recipe — hosted deltas

The list → address → resolve loop, the op shapes, and orphan handling are documented once, runtime-agnostically, in references/comments.md — that is the canonical recipe. This section carries only what is different when the doc is served over the Worker rather than locally:

  • Repo path segment. A hosted doc URL is https://<worker-host>/<repo>/<path>?comments — the <repo> segment the local route omits.
  • Ref semantics. Add &ref=<branch|sha> to pin a non-default ref; omit it and the collection resolves against the repo's default branch.
  • Bearer required. Every request needs Authorization: Bearer $GH_TOKEN with read access to the repo; a local doc needs none.
  • No agent create in v1. Creating comments is a reviewer (browser) affordance. The API does not structurally block a bearer create today, but it is deliberately out of the agent's v1 verb set — a bearer-authored create would land a {"login":"agent"} row. Stick to list / resolve / reopen / delete.
  • One access probe per batch. The gate probes GitHub once per request, so batching several ops for the same doc pays a single probe — see § Ops.

Doc-view widget injection

When a reviewer opens a doc (a normal doc view, no ?comments), the Worker serves the raw doc and — on a 200 text/html response only — appends the review widget plus an inline JSON seed of that doc's comments (open and resolved, each carrying its resolvedAt) to <body> via HTMLRewriter. The page therefore paints with its comments already present, zero extra round trips. The local server produces the byte-identical fragment by string-splicing before </body> — both call the same shared seedJsonScript/widgetScriptTag helpers, so the injected markup can't drift between runtimes, and the seed's </script>-breakout escaping lives once in the shared helper.

This matters to an agent only as context: the seed is the same data the GET API returns, delivered inline for the browser. Drive comments through the API, not by scraping the seed.

The neutral 404

Before serving a doc or touching the comment store, the Worker runs a single access probe: one GitHub Contents request with the caller's token, status line only, once per request (a batch clears it once for all its ops). GitHub 200 (or a future 304) means the caller can see the doc; every other status — including both 403 and 404 — collapses to the same neutral 404 with the body Not found or no access. A doc you can't see is indistinguishable from one that doesn't exist, so comments never leak a doc's existence. The neutral-404 path emits no widget and no seed. A credential-less request is the one exception: it gets a 401 (authenticate), still pre-probe, still non-leaking.

Forward-looking / deferred

  • Hosted browser review now ships (was deferred). The Worker serves the checked-in widget bundle publicly at WIDGET_SRC (/__htmldocs/comments.mjs), registered before any doc parsing/auth so it can never leak a doc's existence; the shared HttpCommentsStore (src/comments/adapters/http-store.ts, built by both runtimes) drives the ?comments body-op API over fetch with the session cookie; and main.ts selects the hosted vs. local runtime off the injected seed's top-level author (present only on the hosted path, so local behavior is byte-identical). The one remaining degraded path: a hosted session whose identity resolution failed seeds without an author and falls back to the fixed local author label (the store is the same either way) — rare, and it matches the sanctioned author-discriminator.
  • Discovery / prompting integration. This doc is pass-1; whether the SKILL.md pointer is the right or only way an agent finds this flow is revisited as the skill's review flow tightens.
  • Probe caching. A short-TTL per-(caller, repo, ref, path) probe cache is a documented lever if bursty agent runs ever pressure GitHub's rate limit — not built in v1.
  • reply / edit. Reserved in the op envelope; a future deliverable can light them up without a schema change.
