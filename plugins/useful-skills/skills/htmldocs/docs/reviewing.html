What this is

The htmldoc-review Cloudflare Worker (proxy.html) proxies requests for HTML documents and supports Review 2.0, a collaboration layer: anyone with access to a doc can review it — in the browser, through a UI the server injects into the page, or programmatically over an HTTP API. The API and the UI are shared between the hosted Worker and a locally run server; only the implementations behind them differ.

Because the Worker fetches each doc from GitHub as the logged-in viewer, GitHub itself is the authorization engine — a reviewer sees, and can comment on, only the docs they can already reach (see proxy.html § What it does). The local server is the same review system without that gate: it serves a file tree on 127.0.0.1 for single-user review.

One surface, two backings. Neither caller — human in the browser or agent over HTTP — needs to know whether the doc is hosted or local. The design record and PR-by-PR history live in d2-review-mode-plan.html; the local widget's component architecture is in review_system.html.

The API surface

A doc's comments are body-ops over one collection URL: the doc's own URL with a ?comments marker. There is no separate comment path.

The URL up to that marker follows the ordinary proxy URL semantics — repo as the first path segment, doc path as the remainder, optional ?ref= for a branch, tag, or SHA (omit it for the repo's default branch), documented in proxy.html § What it does. Unique to the review system are the &comments marker and the request/response bodies below. 

GET  https://<host>/<repo>/<doc-path>?ref=<ref>&comments
POST https://<host>/<repo>/<doc-path>?ref=<ref>&comments

The &comments marker forks the request from "serve the doc" to "the comment API". If the doc URL already carries a ?ref=, keep it and append &comments.

Listing

GET returns the doc's full comment set, open and resolved, ordered by creation time:

200 { "threads": [ Thread, ... ] }

A Thread is:

{
  "id":        "<threadId>",
  "anchor":    { "exact": "...", "prefix"?: "...", "suffix"?: "...", "sections"?: ["..."] },
  "root":      { "id": "<commentId>", "author": { "login": "...", "name": "..."|null, "id"?: 0 },
                 "body": "...", "createdAt": 1720000000000 },
  "replies":   [],
  "resolvedAt": 1720000009999 | null      // epoch-ms; null == open, a number == resolved
}
Timestamps are epoch-millisecond numbers end to end (createdAt, resolvedAt) — never ISO strings on this API. anchor.exact is the quoted doc text the thread pins to; anchor.sections lists the <article id> values the selection intersected (metadata, useful for grouping). replies is always [] in v1 — threads are single-comment.

Mutating

POST a single op object to apply one mutation. The v1 op set:

opBodyEffect
create{op:"create", anchor:{exact, prefix?, suffix?, sections?}, text, clientOpId?}New anchored thread.
resolve{op:"resolve", threadId}Soft-close: stamp resolvedAt, keep the row, indicator turns green, thread stays visible. Reversible.
reopen{op:"reopen", threadId}Clear resolvedAt (idempotent).
delete{op:"delete", threadId}Hard purge by thread id — gone for good.
reply / edit—Reserved in the op envelope: parsed, then rejected 400 {"error":"op not yet supported"}. A future deliverable can light them up without a schema change.

Single-op responses:

200 { "ok": true, "op": "resolve", "thread": Thread }        // resolve / reopen
200 { "ok": true, "op": "delete",  "threadId": "..." }       // delete
200 { "ok": true, "op": "create",  "thread": Thread }        // create
404 { "ok": false, "op": "resolve", "error": { "code": "not_found", "threadId": "..." } }
400 { "error": "op not yet supported" }                      // a single reserved op
400 { "error": "<why>" }                                    // malformed envelope (BEFORE any store write)

Batching

To apply several ops in one request, POST a JSON array of op objects to the same endpoint. A batch is best-effort per op (no cross-op transaction) and always returns 207 with a results array: 

POST [ {op:"resolve", threadId:"a"}, {op:"resolve", threadId:"ghost"}, {op:"delete", threadId:"b"} ]
207 { "results": [
       { "ok": true,  "op": "resolve", "thread": {...} },
       { "ok": false, "op": "resolve", "error": { "code": "not_found", "threadId": "ghost" } },
       { "ok": true,  "op": "delete",  "threadId": "b" }
] }
Correlating results to ops. Results return in request order — the i-th result belongs to the i-th op. In addition, every op that names a threadId (resolve, reopen, delete) echoes it back in its result, including in a failed result's error object. A create has no id until it succeeds, so a failed create correlates by position alone.

How the agent uses it

An agent drives comments over exactly the API above — one client, one call shape, parameterized only by the doc URL (and, for a hosted doc, a bearer token).

The agent-facing prompt recipes live in references/comments.md: the list → address → resolve loop driven through scripts/comments-api.sh (the transport helper the recipe is built around), the op shapes, and the raw curl forms kept in its appendix for environments without bash — the canonical recipe home, with this document as the system reference behind it. The v1 convention is that an agent drives list / resolve / reopen / delete while create is for a human in the browser — a convention, not an enforcement.

Widget injection

When a reviewer opens a doc as a normal page (no ?comments), the server returns the raw doc with the review widget and an inline JSON seed appended to <body>. The seed is { threads, author }: every thread — open and resolved, each with its resolvedAt, so the page paints with its comments already present — plus the author identity the widget stamps onto new comments. The widget mounts only when the seed is present in the DOM; a page served without it renders as plain HTML.

The seed's threads are the same data the GET API returns, delivered inline for the browser's first paint — a rendering convenience, not a second interface. Drive comments through the ?comments API, never by scraping the seed. How each runtime performs the injection, keeping the markup byte-identical, is in § Implementation details.

Authenticating

Every ?comments request is authenticated. Two credentials, one gate:

CallerCredentialHeader / cookie
Browser widget (a human reviewer) the Worker session Cookie: sid=<session> (set by OAuth login; refreshed transparently)
Agent a GitHub token (PAT or installation token) Authorization: Bearer <github-token>

Bearer wins if both are present, and is used as-is against GitHub — an agent token is not a session, so there is nothing to refresh. A locally served doc needs no credential at all.

One gate, always enforced

Authorization has a single chokepoint: checkAccess in src/worker/access.ts, which answers one question — "can this token see this doc on GitHub?" — with one GitHub Contents probe. It is called once, at the single post-authentication site in src/worker/index.ts, before the request forks into "serve the doc" versus "the comment API". Every ?comments path therefore passes through the same gate; even a malformed envelope reaches the store only after the gate clears, so a would-be 400 is still decided behind the access check.

The probe grants on GitHub 200 (or a future conditional 304); every other status, including both 403 and 404, collapses to one neutral 404 with the body Not found or no access. A doc you cannot see is indistinguishable from one that does not exist, so comments never leak a doc's existence. A request with no credential gets an honest 401 before the probe — uniform across every path, and equally non-leaking.

Author attribution. The author on any comment is stamped server-side, never from the request body. For a browser session it is the reviewer's captured GitHub identity. For an agent, a bearer mutation resolves the caller's real identity: the Worker issues GET /user with the presented token and stamps the real {login, name, id}. Listing (GET) is identity-free and issues no such call. The cost is two upstream GitHub calls per mutation — the access probe plus the /user lookup; caching identity by token hash is the named future optimization, deliberately not built in v1.

Implementation details: local vs. Worker

Everything above is shared. The two runtimes diverge only in how they store comments, gate access, and inject the widget — at a glance:

ConcernHosted WorkerLocal server
Comment storeCloudflare D1 (one shared database, migrated from migrations/0001_create_comments.sql)A per-doc sidecar JSON file on disk (a durable backup, not the interface)
Access / authGitHub-gated per viewer (session cookie or bearer), via the access probe aboveNone — single-user 127.0.0.1
Widget injectionHTMLRewriter streaming appendString-splice before </body>
Comment authorCaptured GitHub identity (session) or the bearer caller's resolved identityA fixed local author label
URL shapeCarries a <repo> path segmentNo repo segment — a file path under the served root, plus ?comments

Both runtimes build the injected markup from the same shared helpers, so the widget <script> tag and the JSON seed — including the seed's </script>-breakout escaping — cannot drift between them. The seed shape is identical too: { threads, author }, with author always present — the local server stamps a fixed local author, the hosted Worker the session's GitHub identity. The browser adopts whatever author the seed carries and builds one HttpCommentsStore either way; nothing in the bundle branches on runtime.

Worker specifics

The Worker's comment store is scoped per (repo, ref, path), backed by two distinct stores: sessions live in Workers KV (sess:<id>, native TTL), comments in D1. They evolve by different mechanisms and should not be conflated; an agent reaches only comments, through the ?comments API.
