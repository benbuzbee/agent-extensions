Overview

Add a native SVG output target to tech-diagrams so a YAML spec can be rendered directly to an inline <svg> string without going through Excalidraw JSON. The Excalidraw path stays — SVG becomes a parallel emitter sharing the same validate → desugar → ELK layout pipeline.

Motivation: the htmldocs skill embeds diagrams as inline SVG inside <figure> elements. Today the only programmatic path from a YAML spec to SVG runs Excalidraw JSON through the external excalirender binary (see references/companions.md) — a headless-browser round-trip with a binary dependency. A native emitter removes that hop and produces crisper output (no rough.js jitter, sharper lines) suited to documentation.

How it fits today's architecture

The pipeline already separates layout from rendering. layout/run.ts returns a renderer-agnostic LaidOut tree (absolute pixel coords on nodes, label boxes, edge sections with bend points). The new emitter sits at the same seam as render/to-excalidraw.ts, consuming the same input.

What LaidOut already provides

The LaidOut interface is renderer-agnostic and maps directly to SVG primitives:

ELK outputSVG primitive
LaidOutNode (rect/ellipse/diamond)<rect> / <ellipse> / <polygon>
LaidOutLabel with x,y,w,h<text> positioned by label box
LaidOutEdge.sections[].{startPoint, bendPoints, endPoint}<polyline> or <path>
arrowhead style (per edge)one <marker> per style in <defs>, referenced via marker-end
scene bboxcomputed viewBox

Excalidraw-specific machinery that SVG drops

Most of render/to-excalidraw.ts exists for the Excalidraw scene model or to compensate for excalirender's PNG export. None of it applies to native SVG:

  • seed, versionNonce, updated, roundness enum — Excalidraw scene fields.
  • boundElements, containerId, groupIds — editor binding so dragging a node carries arrows. Irrelevant in static SVG.
  • appendCornerSpacers + inkBounds — exists because excalirender sizes the canvas from raw element bboxes and clips ink. A proper viewBox makes the entire mechanism unnecessary.
  • ARROWHEAD_RADIUS, TEXT_ASCENT_PAD — empirical pixel calibration against the PNG export. Gone.
  • sampleSpline for ink-bounds — needed for excalirender's bbox math, not for drawing.
  • fillStyle: "hachure", roughness — the hand-drawn look. SVG output is intentionally crisp.

Theming & colour

Every emitted SVG is self-themed: the root carries class="tg-svg" and inlines a <style> block declaring a CSS-variable palette plus a @media (prefers-color-scheme: dark) override. Default leaf fill is none so the host page background shows through; edge-label halos and outline-marker inner fills follow a --tg-halo variable that flips with mode. Hex presentation attributes remain on every element as a fallback when the style block is stripped.

See src/render/colors.ts (palette, classes, themeStyleBlock()) and src/render/to-svg.ts (wiring) for the source of truth.

Plan

  1. New emitter at src/render/to-svg.ts. Pure function toSvg(diagram: Diagram, laidOut: LaidOut): string mirroring toExcalidraw's signature.
    • Walk nodes in document order so containers render under their children (same z-stacking trick as to-excalidraw.ts).
    • Reuse expandLabels, pickBoundLabelIndex, and the colour helpers from render/colors.ts for parity with the Excalidraw emitter.
    • Emit one <marker> per arrowhead style actually used, keyed by style so unused markers don't appear in <defs>.
    • Compute viewBox by unioning node bboxes and all edge points (including bend points). Add a small padding constant (no spacer hack).
  2. CLI wiring in src/cli.ts. Infer format from the -o extension: .svg routes to to-svg, .excalidraw routes to to-excalidraw. Add an explicit --format svg|excalidraw override. Default behaviour unchanged when no extension hint is present.
  3. Tests at test/render-svg.test.ts. Snapshot one fixture per genre (architecture, dataflow, state, class, ER) from test/fixtures/. Add a parse check (the emitted SVG must round-trip through a DOM parser without errors) and a determinism check (two runs produce identical strings).
  4. Docs. Add a one-line mention of the SVG target in SKILL.md's render step. Mark excalirender in references/companions.md as optional for SVG (still relevant for PNG/PDF).

Acceptance criteria

CriterionPass condition
Renders every fixture For each YAML in test/fixtures/ that is valid, tsx src/cli.ts render <f> -o /tmp/out.svg exits 0 and writes a non-empty file.
SVG parses cleanly Output round-trips through a DOM parser with no <parsererror>; root element is <svg> with a numeric viewBox.
Byte-deterministic Two runs of the same input produce identical output bytes (matching the determinism guarantee already enforced for the Excalidraw emitter).
All shapes supported Rectangle, ellipse, and diamond nodes from existing fixtures render with correct geometry.
Edge styles supported Dashed strokes, stroke colour, and start/end arrowhead variants present in fixtures all emit correctly.
Labels positioned Node labels and edge labels appear at the ELK-resolved coordinates; bound node labels centre on their shape.
Container nesting Parent containers render behind their children; nested fixtures (e.g. groups-nested.yaml) visually enclose their members.
viewBox encloses all ink No node, label, or bend point lies outside the emitted viewBox bounds, with padding ≥ stroke width.
Self-contained output Emitted SVG references no external CSS, fonts, or scripts. Inline only.
Excalidraw path unchanged Existing snapshot tests for to-excalidraw pass without modification.
CLI inference works A new CLI test confirms -o foo.svg selects the SVG emitter and -o foo.excalidraw selects the Excalidraw emitter without explicit --format.

Non-goals

  • Hand-drawn / sketchy aesthetic. SVG output is intentionally crisp. Users who want the rough.js look stay on the Excalidraw path.
  • Dual-format files. No attempt to produce one file that opens in excalidraw.com and renders as inline SVG. Separate emitters, separate outputs.
  • PNG/PDF. Still handled by excalirender via the Excalidraw path. The SVG emitter is for inline embedding, not raster export.
  • Interactivity. No hover tooltips, no JS, no click handlers — htmldocs's self-contained-files principle forbids JS in docs.
